# 库存数量支持小数：迁移与实施方案（历史设计）

> 历史归档：本文是 v11 数量精度的设计记录，功能已实现并上线；命令与路径可能已过时，勿照做。
>
> 状态：**已实现（schema v11，数量 4 位定点整数 ×10000）**。
> 基准提交：`f81a383`（schema v10）。

## 1. 结论与总体选择

- 数量统一用 **4 位小数的定点整数**存储，比例为 `SCALE = 10000`，即 1 个单位存成 `10000`。
- 全部数量运算使用 `std::int64_t`，代码里不出现 `float` / `double` / `std::stod`。
- **不重建表**：SQLite 的列类型只是亲和性，`qty` 列本来就声明为 `INTEGER`，改成「定点整数」只改单位语义，不改列类型。v11 只需 `ALTER TABLE unit ADD COLUMN` 加一列精度，再对四张表做一次 `UPDATE ... * 10000`。
- 金额（分）不动：迁移不重算任何历史金额，历史单据的金额与单据号保持原样。
- API 的数量字段改为**十进制字符串**（如 `"12.3456"`），避免 JSON 数字被解析成浮点；前端用字符串拆分换算成整数。
- 展示层统一 `qty_text()`：最多 4 位小数、去掉末尾 0，整数仍显示为整数。

选 4 位而不是 3 位：千克 3 位够用，但米、卷材、面积类常需要第 4 位；多留一位不增加复杂度，只是把 `SCALE` 定为 10000。

## 2. 受影响列（已逐一核对）

| 表 | 列 | 处理 |
| --- | --- | --- |
| `doc_header` | `total_qty` | ×10000 |
| `doc_line` | `qty` | ×10000；`CHECK (qty > 0)` 放大后仍成立 |
| `doc_line` | `converted_qty`（订单已转出数量） | ×10000 |
| `stock_balance` | `qty` | ×10000 |
| `stock_ledger` | `qty` | ×10000；`CHECK (qty <> 0)` 放大后仍成立 |
| `unit` | 新增 `qty_decimals` | 0–4，内置单位按第 3 节赋值 |

不需要改的：

- `ar_ap_entry`、`settlement`、`settlement_allocation`：只有金额（分），与数量无关。
- `doc_seq`（单据号）、`audit_log`、`print_template`：不受影响。
- 订单剩余量没有独立列，由 `qty - converted_qty` 派生，两边同时放大，差值语义不变。
- 没有名为 `qty_change` 的列；库存变动只有 `stock_ledger.qty`（正负号表示方向）。

## 3. 单位精度

`unit` 表新增：

```sql
ALTER TABLE unit ADD COLUMN qty_decimals INTEGER NOT NULL DEFAULT 0
  CHECK (qty_decimals BETWEEN 0 AND 4);
```

内置单位赋值（按 v4 的种子行）：

| 单位 | 小数位 |
| --- | --- |
| 件、瓶、个、箱、包 | 0 |
| 米 | 2 |
| 千克 | 3 |

规则：

- 录入校验：数量必须是十进制文本，小数位 **不超过该商品单位的 `qty_decimals`**，否则拒绝并提示「千克最多 3 位小数」。整数位上限 9 位。
- 数量的「精确值」就是解析出来的定点整数，**不做四舍五入**：用户输入 1.2345 且单位允许 4 位时，存 12345；单位只允许 3 位时直接报错，而不是悄悄截断。
- 商品 `unit_id = 0` 的历史行没有单位档案：精度按 0 处理（只能录整数），在商品页提示补选计量单位。可选的回填步骤见第 6 节。
- 展示：`qty_text(int64)` 输出 `整数部分.小数部分`，去掉末尾 0，最多 4 位；不带千分位，方便复制到 Excel。打印、CSV、XLSX 全部走这一个函数。
- 只有**金额**在行级做一次四舍五入：`line_amount = round_half_up(qty_scaled * price_cents / 10000)`。数量本身永不取整。

## 4. 成本与金额算法

### 4.1 公式

```text
入库 / 采购退货 / 其他入库：
  amount_cents = round_half_up(qty_scaled * price_cents / 10000)

出库 / 销售 / 其他出库（移动加权平均）：
  cost = (balance_amount_cents * qty_scaled + balance_qty_scaled / 2) / balance_qty_scaled   // 整数除法
  cost = clamp(cost, 0, balance_amount_cents)
  若本次出库把余额清零（qty_scaled == balance_qty_scaled），cost = balance_amount_cents

盘点：
  diff = 实盘_scaled - 账面_scaled
  diff > 0 时按移动加权平均入账（账面为 0 时用录入单价）
  diff < 0 时按移动加权平均出账

单位成本（仅展示）：
  unit_cost_cents = round(qty_scaled ? balance_amount_cents * 10000 / balance_qty_scaled : 0)
```

`round_half_up` 用整数实现：`(numerator + 5000) / 10000`（`numerator >= 0`；负数先取反再回加符号）。加 `balance_qty/2` 的写法与原实现一致，仍是整数加整数再整除。

### 4.2 用例（单位：分 / 千克）

| 步骤 | 数量（定点） | 单价 | 本次金额/成本 | 余额数量 | 余额金额 |
| --- | --- | --- | --- | --- | --- |
| 入库 10.5 kg | 105000 | 1234 | 12957（10.5×1234 恰好整除） | 105000 | 12957 |
| 入库 3.25 kg | 32500 | 1200 | 3900 | 137500 | 16857 |
| 出库 4 kg | 40000 | — | 4904（16857×40000+68750=674348750 ÷137500=4904.35） | 97500 | 11953 |
| 出库 9.75 kg（清零） | 97500 | — | 11953（清零规则取剩余金额） | 0 | 0 |
| 销售 1.5 kg @ ¥20.00 | 15000 | 2000 | 3000 | — | — |
| 盘点实盘 8.2525 kg，账面 8.25 kg | +25 | 1226 | 3（0.0025×1226=3.065→3 分） | — | — |

误差分析：

- 单次出库舍入误差 ≤ 0.5 分，且余额金额始终等于「累计入库金额 − 累计出库成本」，不会出现独立漂移。
- 清零时把剩余金额整笔结转，误差不跨批次累积：一个商品在一个仓库里，历史累计误差只体现为当前余额金额相对「精确理论值」的 ±0.5 分。
- 盘点差额金额同样只影响本行，不修改历史流水。

## 5. 迁移方式（v11）

### 5.1 为什么不重建表

SQLite 的 `INTEGER` 列可以存任意 64 位整数，改「单位」不需要改声明类型。四张表的 `CHECK` 约束（`qty > 0`、`qty <> 0`）在乘以 10000 后仍然成立，索引与主键也不用动。相比「重建表 + 回填 + 换名」，这样做没有外键重写风险（`doc_line` 引用 `doc_header`，重建 `doc_header` 会改写引用），也不会重建索引。

### 5.2 迁移 SQL（完整）

```sql
-- v11：数量改为 4 位定点整数（×10000），金额仍为分。
-- 只新增单位精度列并放大存量数量，不改列类型、不重算金额。

ALTER TABLE unit ADD COLUMN qty_decimals INTEGER NOT NULL DEFAULT 0
  CHECK (qty_decimals BETWEEN 0 AND 4);

UPDATE unit SET qty_decimals = 2 WHERE code = 'MI';
UPDATE unit SET qty_decimals = 3 WHERE code = 'KG';

UPDATE doc_header    SET total_qty = total_qty * 10000;
UPDATE doc_line      SET qty = qty * 10000,
                         converted_qty = converted_qty * 10000;
UPDATE stock_balance SET qty = qty * 10000;
UPDATE stock_ledger  SET qty = qty * 10000;
```

### 5.3 版本、checksum 与备份

- 迁移由既有 `migrate()` 执行：整段 SQL 在一个 `BEGIN IMMEDIATE` 事务里，失败整体回滚，不会出现「放大了两张表、另两张没放大」的中间态。
- `schema_migration` 写入 `(11, v11_decimal_qty, checksum)`，同时 `PRAGMA user_version = 11`，与 v1–v10 完全一致；已发布迁移不可改，改了会报 `MIGRATION_CHECKSUM`。
- 迁移前自动备份已覆盖这条路径：`cli_main.cpp` 在 `previous_version < target_schema_version()` 时先写 `backups/app-<时间>-pre-v10.db`，再迁移。v10 → v11 会触发，无需额外改动。
- 回滚：停服 → `--restore` 迁移前备份 → 换回旧二进制。**不能只回退二进制**：旧程序会把放大后的数量当成原数量显示。
- 迁移 SQL 为纯增量语义，但对同一库重复执行会二次放大；因此只能依赖版本号执行一次，不做「幂等重跑」。

### 5.4 可选的单位回填（建议做，单独确认）

v4 之前创建的商品 `unit_id = 0`，只有 `unit` 文本快照。可以按名称唯一匹配回填：

```sql
UPDATE item
SET unit_id = (SELECT u.id FROM unit u
               WHERE u.name = item.unit AND u.is_deleted = 0 LIMIT 1)
WHERE unit_id = 0
  AND EXISTS (SELECT 1 FROM unit u
              WHERE u.name = item.unit AND u.is_deleted = 0);
```

风险：同名单位存在多条时取第一条。更保守的做法是不回填，由用户在商品页补选单位；`unit_id = 0` 时精度按 0 处理。**这一条请明确是否要做。**

## 6. 兼容与风险

- **历史单据**：数量放大、金额不变。展示时 `qty_text()` 去掉末尾 0，旧单据看到的仍是原来的整数数量。单据号、审核时间、审计日志都不变。
- **历史报表**：报表 SQL 的 `SUM(qty)` 在定点整数上求和，结果除以 10000 展示，历史区间数字不变。`sales_profit` 的营收改为 `SUM(l.amount_cents)`：历史行 `amount_cents` 等于 `qty*price`，结果与原来一致；新行也避免了「按数量反算营收」的二次舍入。
- **应收应付 / 核销**：`ar_ap_entry.amount_cents` 与 `settlement` 只涉及金额，不受影响；单据审核时写入的金额仍是行金额之和，规则不变。
- **订单**：`remaining_qty = qty - converted_qty` 仍按定点整数算，转出校验、关闭订单条件（`converted_qty < qty`）同步改单位。旧订单放大后剩余量语义不变。
- **库存不足校验**：`balance.qty >= need` 改为定点整数比较，没有容差；提示文案用 `qty_text()`，例如「库存 3.5，需出库 4」。
- **盘点零数量**：现有 `doc_line CHECK (qty > 0)` 与「盘点允许 0」本来就冲突（0 会被数据库拒绝）。本次**不改变**这条约束，避免扩大改动面；如果确认要允许实盘 0，应另开一笔迁移处理。
- **并发**：单写连接 + `BEGIN IMMEDIATE` 的前提不变；压测脚本要补小数数量场景（例如 0.5、1.25、3.333 kg），继续核对单据号唯一与余额一致。12/29 并发的结论需要在改完后重跑一遍。
- **溢出**：`qty_scaled` 上限建议 1e10（即 100 万个单位），`price_cents` 上限 1e8（¥100 万），乘积 1e18 < int64 上限；前端金额预览用 `BigInt`，不受 2^53 限制。
- **数据目录 / 会话**：与本次无关；迁移不清会话表。

## 7. 「不引入浮点」的保证

| 层 | 做法 |
| --- | --- |
| 数据库 | `INTEGER` 存定点整数；SQL 中只做加减乘与整数除法 |
| C++ | 新增 `core/include/xiaotu/qty.h`：`using Qty = std::int64_t; constexpr Qty kQtyScale = 10000;`，只提供整数解析/格式化/乘法/加权平均；禁止 `double`、`float`、`std::stod`、`atof` |
| 校验 | `parse_qty(std::string_view, int decimals, bool allow_zero, std::string_view label)` → `std::optional<Qty>`：手写字符扫描，拒绝 `+`、指数、多于允许位数 |
| JSON 入参 | 数量字段按字符串传入（`"qty": "1.25"`），`nlohmann::json` 不解析成数字就接触不到浮点 |
| JSON 出参 | `qty_text()` 输出字符串；`total_qty`、`remaining_qty`、报表 `qty` 字段同 |
| 金额 | 行金额在服务端用整数 `(qty*price + 5000) / 10000` 得到分 |
| 前端 | 录入用 `type="text" inputmode="decimal"`，正则校验后拆整数/小数拼成整数；金额预览用 `BigInt`，最后 `toString()`；展示用 `qtyText()` 做整数除法与补零，不做 `toFixed` |
| CSV | 数量列输出 `qty_text()`；金额列沿用现有两位小数 |
| XLSX | 数量列写成**文本单元格**（`XlsxCell::text`），避免数值单元格把十进制转成二进制浮点；代价是 Excel 里不能直接求和。若必须求和，另加「整数+4 位缩放」的数值列，不改变事实来源 |
| 打印 | 模板列定义与宽度不变，渲染时按 `qty_text()` 输出 |
| 报表比率 | `sales_profit` 的毛利率目前用 `double`；改为整数万分比（`profit*10000/revenue`），展示时按整数插小数点 |

## 8. 实施顺序（确认后执行，小步提交）

1. `qty.h` + 单测：解析、格式化、金额乘法、加权平均（含第 4.2 节用例）。
2. v11 迁移 + 迁移测试：v10 库放大后数量/金额核对、`user_version = 11`、checksum 记录。
3. 核心业务：单据校验、行金额、成本、库存不足、订单转出、盘点；补 core_smoke 小数用例。
4. 报表与导出：SQL 求和口径、CSV/XLSX、打印渲染、毛利率改整数。
5. 前端：单据与订单的数量录入/展示、库存与报表页、`qtyText` 与 `BigInt` 金额预览。
6. 压测脚本补小数场景并重跑；README 与用户手册同步「数量支持小数、单位小数位」。

## 9. 需要确认的点

1. `SCALE = 10000`（4 位）是否按此定稿。
2. 内置单位小数位：米 2、千克 3，其余 0，是否符合实际业务。
3. 数量字段在 API 上改为**字符串**（推荐，彻底避开浮点）还是保留数字但约定为定点整数。
4. 是否执行 5.4 的 `item.unit_id` 按名称回填。
5. 盘点实盘为 0 目前会被 `CHECK (qty > 0)` 拒绝，是否本次一并放开（需要额外改约束）。
6. XLSX 数量列先按文本导出（不可直接求和），是否接受。
