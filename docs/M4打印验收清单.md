# M4 打印验收清单

验收对象：打印模板（纸张 / 边距 / 方向 / 缩放 / 打印列）、导出 PDF、CSV/XLSX 数字一致性。
数据库结构版本：v29（打印规则自 v27 起）。
本次离屏验收：2026-11-13，macOS 15.8.2；临时数据目录 `/tmp/xt-print/data`，未触碰真实数据目录。

## 结论摘要

| 项目 | 结论 |
| --- | --- |
| 纸张尺寸 / 方向 | 已验通过：6 份样张 MediaBox 与模板纸型偏差 ≤ 0.10 mm |
| 列宽累加 | 已验通过：列边界严格按模板列宽累加，按实际比例折算后残差 ≤ 0.19 mm |
| 页边距 | 未通过：左边距 0.13～0.14 mm（模板 12），内容顶部 0.35 mm（模板 12） |
| 表头 / 表体字号 | 未通过：单页纸比 `layout.effective_font_pt` 大 6.7%（10pt → 10.68pt）；241 采购明细因整页缩到 95.5%，反而小 4.4%（10pt → 9.56pt） |
| 连续纸原始尺寸 | 未通过：241×140 采购明细被整体缩到 95.53%（10pt → 9.56pt），与「不会自动缩放」的告警文案矛盾 |
| 应用内导出 PDF | 本机未通过：同链路 `runOperation` 产出空白页；改用 `runOperationModalForWindow` 才能得到有效 PDF |

实测到的两条渲染行为：

1. WKWebView 打印时忽略 `NSPrintInfo` 的四边 margin 和居中设置；前端在原生模式下又把 `@page margin` 设为 0（`web/app.js` 479–480 行），叠加后 PDF 边距为 0。
2. WKWebView 对整页施加隐式缩放：基线 1.067 倍（CSS 10pt → PDF 10.68pt）；整页宽度超过纸宽时再整体缩到纸宽（241×140 采购明细为 1.067 × 0.896 ≈ 0.955）。

- 单页纸默认「按纸宽自适应」，只缩版式（CSS `zoom`），不改数值；缩放后有效字号低于 7pt 时返回 `font_too_small`。

## 五、验证方法与限制

### 1. 样张数据

- 临时数据目录：`/tmp/xt-print/data`（`--data` 启动，真实数据目录未参与）。
- 商品 2 个、供应商 1 个、仓库 1 个；采购入库单 1 张，2 行明细：10 件 × 12.50 元 + 3 件 × 48.00 元 = 13 件 / 269.00 元，状态已审核。
- 打印模板 3 种：A4 纵向 `FIT_WIDTH / SHEET / margin 12`；A4 横向 `FIT_WIDTH / SHEET / margin 12`；241×140 `ORIGINAL / CONTINUOUS / margin 12`。
- 样张与解析数据：`/tmp/xt-print/pdf/`（6 份 PDF + 对应的 `*.json` 布局与分析结果）。

### 2. PDF 生成链路

- 启动临时服务，用离屏 WKWebView 加载真实前端页面，登录后点击真实「打印」按钮；打印视图、CSS、`/api/print/render` 数据均与应用内一致。
- 原生侧复制 `shell/mac/webview.mm` 的 `XiaotuApplyPaper` 逻辑：`paperSize` 按模板 mm 换算、四边 margin 换算、关闭居中、`NSPrintSaveJob`。
- 因本机 `runOperation` 产出空白页（见下），几何样张改用同一 `NSPrintInfo` 的 `runOperationModalForWindow` 生成；打印视图与纸型参数不变。

### 3. 测量方法

- 用 PyMuPDF 读取 `page.rect`（MediaBox）、`get_drawings()` 的表格边框线、`get_text("dict")` 的 span 坐标与 `size`。
- 坐标换算：mm = pt × 25.4 / 72。
- 列边界取表头区域内的细竖线中心；字号取表头行/表体行 span 的 `size`；上边距取页面最上方文字墨迹的 `bbox.y0`。

### 4. 本次发现的两个链路阻塞（事实记录）

1. **报表打印 URL 拼接**：`periodQuery()` 返回以 `?` 开头的串（`web/app.js` 3206–3208 行），`purchaseQuery()` 直接前缀拼接（3268–3273 行）；打印 URL 又在 `target_key=purchase-detail` 后直接拼接（3897–3903 行），实际请求变成 `target_key=purchase-detail?from=…`，服务端返回「未知的打印目标」。本次离屏驱动在 fetch 层把该 `?` 改写为 `&` 后才取到采购明细打印视图；未修改仓库代码。
2. **`runOperation` 空白页**：在同一台机器、同一 WKWebView、同一 `NSPrintInfo`（A4 595×842、四边 34.02pt）下，`[operation runOperation]` 生成大量空白页；`runOperationModalForWindow` 生成 1 页有效 PDF。`shell/mac/webview.mm` 160 行的 PDF 导出走的正是 `runOperation`，该路径需在真实应用窗口复核。

## 六、页码能力实测（2026-11-13）

| --- | --- | --- |
| `@bottom-right` margin box | 3 | 3 页均只有正文，页码出现 0 次 |
| `createPDF`（同一 HTML） | 1 | 单页连续快照，页码不渲染 |
| `position: fixed` 页脚 + `counter(page)` | 3 | 页脚只在末页出现，解析为「第 0 页」；前两页无页脚 |

**结论**

- WKWebView 打印不渲染 `@page` 的 margin box，也不支持 `counter(page)`；`position: fixed` 元素在打印分页中不会逐页重复。
- 因此 `show_page_no` 在 WKWebView 不生效；「HTML 固定页脚」兜底同样不成立。按最小方案落地（2026-11-13）：保留 `show_page_no` 作为提示性字段，不做前端显式分页、不做 PDF 后处理叠页码；模板编辑处提示「页码随打印引擎而定；网络版可在浏览器打印对话框勾选页眉和页脚」。
- 本结论只覆盖上述探针环境；浏览器打印（Safari / Chrome / Firefox）的 margin box 支持各不相同，未逐一实测。
