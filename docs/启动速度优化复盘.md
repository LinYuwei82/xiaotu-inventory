# 启动速度优化复盘

> 日期：2026-11-27 ｜ 版本基线：1.0.16（构建号 12）之后
> 提交：`3562baa` / `724986c` / `75d44ed` / `8cc3167`（均已双推，CI 全绿）

## 1. 背景与目标

用户反馈「启动慢」，未指明平台与阶段。目标：定位双平台（Windows / macOS）启动链路的真实瓶颈，
在「用户可见行为零改动」前提下优化，并留下可持续观测的量化手段。

尺度经确认：**允许结构性改动**，双平台都要优化。

## 2. 启动链路盘点（调研结论）

### 2.1 三段链路

```
双击图标 → 壳（win: xiaotu-shell.exe 拉起 server 子进程 / mac: 单进程内嵌 server）
        → server（配置→锁→Db→迁移→bind→serve）
        → 前端 bootstrap（health→me→pages.json→7 个 gen 脚本→首屏挂载）
```

### 2.2 各段现状与嫌疑点

| 段 | 现状 | 嫌疑点 |
|---|---|---|
| win 壳 | 已并行：窗口先显示 → CreateProcess 拉 server → reader 线程解析 stdout 访问地址 → WebView2 环境初始化与子进程并行 → 双就绪导航，事件驱动无轮询 | 结构已优，剩余在 server 与 WebView2 冷初始化 |
| mac 壳 | **串行**：cli_main 走完 配置→锁→Db→restore→migrate→repair→角色→bind→serve 之后才 `run_webview()` 建窗口 | server 就绪前用户看不到任何东西，感知最差 |
| server | Db 开 5 连接、migrate 正常 no-op、repair 每次启动一个写事务、load_role 小读、备份调度器**启动即跑一次 VACUUM INTO** | repair/备份与首请求抢锁抢盘 |
| 前端 | bootstrap 串行链：health → me → pages.json → **for 循环逐个 await 加载 7 个 gen 脚本** | 8 个纯串行往返 |
| 更新模块 | win 30s 后后台线程、mac dispatch_after 30s | **排除**：不拖慢启动 |
| 观测 | 无任何启动耗时打点 | 无法量化，先建基线 |

## 3. 方案设计与取舍

按收益/风险比分层（P2 项明确不做）：

- **P0-1 启动打点**：先量化后优化。server 五段 elapsed 落 app.log；win 壳写
  `%LOCALAPPDATA%\com.simem.xiaotu\shell-boot.log`（QPC 计时，七个事件点）；mac 壳 NSLog 三点；
  前端 `performance.now()` console.debug。失败全部静默，不影响启动。
- **P0-2 前端并行化**：health∥me∥pages.json 三者并行；7 个 gen 页脚本 Promise.all
  （各页独立注册 `window.XiaotuPages[key]`，无相互依赖，已核实）。
  细节：me 的 401 吞掉语义不变；pages.json 提前取但脚本加载仍在登录成功后；
  登录页分支 pagesPromise 可能无人 await，挂空 catch 防 unhandled rejection。
- **P1-3 mac 窗口先行**：拆出 `show_splash(title)`——建 NSApp/菜单/窗口/WKWebView、
  `loadHTMLString` splash（底色与页面 `--bg #f5f6f8` 一致，窗口本体同色防闪白）、
  泵事件循环 ≤150ms 让首帧落地；`run_webview` 复用同一窗口（`EnsureShellWindow` 幂等）。
  **取舍**：splash 是新增中间态（旧行为是 server 就绪前无窗口），经用户确认接受。
  维护命令（--backup/--restore/--set-password/--partner-preview）不开窗。
  未调 show_splash 时行为与旧版完全一致（回滚安全）。
- **P1-4 repair 后移**：未升版的常规启动把 `repair_customer_credit_mirror` 挪到后台线程；
  migrate 实际升版或新建库仍同步（迁移完立刻修平，语义不变）。
  生命周期用 RAII guard（结构体析构 join）保证异常/各 return 路径不悬挂——
  `std::thread` 析构时 joinable 会 terminate，直接 detach 则 db 栈对象先亡悬空，两者都不可。
- **P1-5 备份首检延时**：DailyBackupScheduler 首次备份前先等 60s（cv wait 可被 stop 打断），
  避开启动期磁盘/写锁竞争；「补当天备份」语义不变。
- **明确不做**：load_role_permissions 并行（单表小读 <1ms）；embedded_web 拆分（内存态已快）；
  win 壳结构再动（已并行）；Defender 排除属打包文档建议。

## 5. 过程中的坑（值得记住）

1. **跨境网络不可靠**：Windows 端 `git clone` GitHub 中途断流（curl 92 stream reset）；
   二次 `git pull` 又被 Connection reset。**解法：git bundle 走局域网 scp**——
   首次全量 bundle，后续增量 bundle（`cfa4019..main`），稳定且快。
2. **macOS 打包传 Windows 全军覆没**：`tar`（即使 COPYFILE_DISABLE=1）Windows bsdtar 报
   `Archive entry has empty or unreadable filename`（AppleDouble 扩展属性条目）；
   `zip` + PowerShell `Expand-Archive` 解压中途失败触发回滚，目标目录被清空。
   **结论：跨平台传仓库一律 git bundle，不要打包文件系统。**
3. **验证了旧二进制**：第一轮 Windows 复验日志里没有打点行——git pull 被 findstr 过滤掉
   错误输出，实际停在旧提交，ctest 20/20 测的是旧代码。**教训：同步后必须核对
   `git log -1` 与预期提交一致，再做构建验证。**
4. **本地残留改动阻塞 ff**：Windows 端 `updater_win.cpp` 有行尾/空白噪声改动导致 merge 被拒，
   `git checkout --` 丢弃后正常。
5. **Windows 控制台中文编码**：`findstr` 匹配中文关键词失败、`dir` 输出 GBK 乱码；
   改用 `powershell Get-Content -Encoding UTF8 | Select-String` 读取日志。
6. **std::thread 生命周期**：栈上 Db + 后台 repair 线程，detach 会悬空、忘 join 会 terminate，
   RAII guard 是 C++ 里最省心的写法（析构顺序保证 join 先于 db 销毁）。

## 6. 遗留与建议

- **真机体感验收**：发版前在两台真机双击实测（win 看 shell-boot.log，mac 看 Console.app 的
  `[xiaotu] 启动打点`），确认 splash→首屏的整体观感。
- **打点常驻**：三段打点已进主干，后续任何「启动变慢」反馈可直接要日志定位到段。
- **可选后续**（收益小，暂不做）：`/gen/*` 响应加缓存头；打包文档建议 Defender 排除数据目录；
  win 壳 WebView2 用户数据目录预热。
- **回滚指引**：四笔提交相互独立，任意一笔可单独 revert；P1-3 若回滚，webview.h 的
  `show_splash` 声明与 cli_main 调用需一并撤。
