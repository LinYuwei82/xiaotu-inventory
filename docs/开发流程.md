# 多机开发流程

项目在三台机器上并行推进：一台家里常开的 Mac、一台办公室的 Mac 笔记本、一台 Windows 机器。本文约定分工、边界、分支与同步纪律，避免几台机器互相覆盖。构建方式、preset 名称见 [README](../README.md) 第 2 节，夜间任务见 [tools/nightly](../tools/nightly/README.md)。

## 1. 分工

| 机器 | 系统与位置 | 负责范围 | 特点 |
| --- | --- | --- | --- |
| `macmini` | macOS，家里 | `core/`、`server/`、`tests/`、`tools/codegen/`、`docs/`，迁移与业务逻辑，schema 演进 | 24 小时开机，主力执行机；长任务、夜间构建都归它 |
| `macbook` | macOS，办公室 | `web/` 的短小交互与样式改动、页面走查、文档校对 | 时间零碎，只做短的交互任务，不跑长时间后台构建；改 `web/` 前与 `macmini` 协调同一文件 |
| `12600k` | Windows，办公室 | `shell/win/`、`packaging/win/` 与 Windows 打包验证 | 负责 Windows 壳、安装包与 Windows 侧构建验证，不改业务逻辑与 schema |

- 跨范围的改动（例如新增一张表的完整链路）由 `macmini` 完成 `core/server/tests/gen`，Windows 侧只做壳的加载与打包，不碰业务实现。
- 需要在另一台的范围内改东西时，先在群里说明，避免同一文件几端同时改。

## 2. 目录边界

| 目录 / 文件 | 谁能改 | 说明 |
| --- | --- | --- |
| `core/`、`server/`、`tests/` | 仅 `macmini` | 业务内核、HTTP 层、迁移脚本、冒烟与单测 |
| `tools/codegen/` | `macmini` 独占 | schema、模板、生成器只在 `macmini` 改 |
| `core/**/gen/`、`server/**/gen/`、`web/gen/` | `macmini` 生成并提交 | 其他机器 `pull` 后直接使用，**不要手改生成物** |
| `web/` | 结构性与生成相关内容归 `macmini`；短小的样式、文案改动可由 `macbook` 做 | 同一文件同一时间只由一方修改 |
| `docs/` | `macmini` | 方案文档、接口约定、流程说明；`macbook` 可校对，改动前先说明 |
| `shell/win/`、`packaging/win/` | 仅 `12600k` | Windows 壳（`shell/win/` 是独立 CMake 工程，不接入根构建）与打包脚本 |
| 根 `CMakeLists.txt`、`shell/CMakeLists.txt` | 仅 `12600k` | `shell/win` 目前是独立 CMake 工程，不接入顶层构建；将来若接入，先与 `macmini` 协调（共享文件） |
| `CMakePresets.json` | `12600k` 默认维护 Windows 相关 preset，`macmini` 维护 macOS preset | 属于共享文件，见下节 |

### 2.1 共享文件

以下四个文件同一时间只由一方修改，另一方需要动时先在群里提出，改完对方再拉：

- 根 `CMakeLists.txt`（新增子目录、改构建目标等）
- `CMakePresets.json`
- `shell/CMakeLists.txt`
- `README.md`

共享文件的改动不夹带在功能提交里，单独一笔提交，提交信息写清动机，方便对方判断是否需要立即同步。

### 2.2 本阶段边界

`macmini` 正在推进 schema v11（数量小数）、v12（收付款与资金账户）、v13（成本调整单）。这段时间 `12600k` 只做壳与打包：不修改业务逻辑、不改 schema，壳只负责加载前端；测试时用哪一版数据库都可以，以能启动、能打开页面为准。

`windows-release` / `windows-dev` preset 都带 `XIAOTU_BUILD_SHELL=OFF`，这是有意保持的现状：该开关只控制 macOS 壳。Windows 壳位于 `shell/win/`，仍可独立 configure；自 `c7e77e6` 起也可用根 `CMakeLists.txt` 的 `XIAOTU_BUILD_WIN_SHELL=ON` 接入顶层构建（默认 OFF、仅 WIN32 生效，非 Windows 只警告并忽略），两者互不影响。默认构建不需要动这两处开关。

生成物边界：所有 `gen/` 与 `cmake/generated_sources.cmake` 由生成器产出，首行带 `AUTO-GENERATED` 标记。其他机器如果发现生成物有问题，改的是「描述问题的文档或 issue」，不是 `gen/` 里的文件；由 `macmini` 改 schema / 模板后重新生成。

### 2.3 PowerShell 脚本编码

仓库内所有 `.ps1`（`tools/win/`、`packaging/win/`、`shell/win/`）统一保存为 **UTF-8 with BOM**。PowerShell 5.1 会把无 BOM 的 UTF-8 按当前 ANSI 代码页（简体中文为 936）读取，中文注释和中文输出会变成乱码，甚至直接解析失败、脚本起不来。编辑时保留开头的前三字节 `EF BB BF`，不要另存为「UTF-8 无 BOM」；细则与判断方法见 [`tools/win/README.md`](../tools/win/README.md) 的「脚本编码约定」。

## 3. 分支规则

- 分支名 = 机器前缀 + `/` + 短任务标记，每台机器只用自己的前缀，不共用：
  - `macmini/商品表单`
  - `macbook/页面走查`
  - `12600k/win-shell`（Windows 壳与打包固定用这个分支）
- 每次从最新 `main` 新建，不长期挂着旧分支：

```bash
git switch main
git pull --rebase origin main
git switch -c 12600k/win-shell
```

- 动手前先 `git pull --rebase`，小步提交；每台机器的提交只在该机器上产生，不代提交。
- 已经推送的提交不再 rebase。需要跟进 `main` 时用合并提交，或另起新分支，避免改写远端历史：

```bash
git fetch origin
git merge origin/main
```

- 合并完成后删除本地与远端分支，其他机器执行 `git fetch --prune` 清掉过期引用：

```bash
git push origin --delete 12600k/win-shell
git branch -d 12600k/win-shell
# 其他机器
git fetch --prune
```

- `main` 保持可构建；不直接在 `main` 上做未完成的改动。

## 4. 合并门槛

合并到 `main` 前，涉及机器都要构建通过，构建不过的分支留在各自分支上，不合并：

1. **ctest 全绿**。macOS 用：

   ```bash
   ctest --test-dir build/release --output-on-failure
   ```

   Windows 用（`binaryDir` 是 `build/windows`）：

   ```bash
   cmake --build --preset windows-release
   ctest --test-dir build/windows --output-on-failure
   ```

   改了 `core/`、`server/`、`tools/codegen/` 时，先按 README 重新配置并全量构建，再跑测试。

2. **手动点一遍改动的路径**：启动对应形态（单机版或 `--server`），把本次改动涉及的页面/接口实际走一遍；涉及单据的，至少走「新建 → 审核 → 反审核」。

3. **Windows 壳能构建并启动**：`shell/win/` 或 `packaging/win/` 有改动时，在 `12600k` 上完成构建与实际启动，确认能加载前端页面。

只改文档或样式的分支也要跑一次构建，确认没有连带破坏。

**CI 的边界**：Gitee Go 只跑 Linux + `XIAOTU_BUILD_SHELL=OFF`（入口 `tools/ci/check.sh`）；GitHub 镜像的 `windows-build.yml` 只在推送到 `main` 后跑 MSVC 服务端构建与 ctest。两条都不含 macOS 壳与 Windows 壳，这些必须在本机实际构建，不能用「CI 绿了」代替。

指定初始化器顺序错误（如 `DocumentDefinition` 的 `.order_converts_to` 写在 `.on_reverse` 后面）只在 MSVC 下以 C7560 暴露，Clang 默认只是告警。根 CMake 已用 `/we7560` 与探测到的 `-Werror=reorder-init-list` 把它升级为错误，但这类问题仍必须由 `windows-build.yml` 实际用 MSVC 编过一次才算真验过；只在 macOS 上编译通过不能作为依据。

## 5. 每日同步纪律

- **开工先 pull**：`git switch main && git pull --rebase origin main`。
- **收工前 commit + push**：当天的工作即使没完成也要落到远端，不留只存在于本机工作区的改动。
- **做到一半用 wip 分支**：未完成、不能进 `main` 的改动推到 `wip/<机器>-<日期>`，例如：

  ```bash
  git switch -c wip/macmini-20261112
  git add -A && git commit -m "wip: 库存流水查询（未完成）"
  git push -u origin wip/macmini-20261112
  ```

  第二天从该分支继续，完成后按第 3 节流程合并、删除；未推送的提交可以 rebase，已推送的用合并提交跟进。
- 不在工作区留跨天的未提交改动；不在多台机器上同时改同一文件。

## 6. 接口契约

- `docs/` 下的接口约定（路由、字段、错误码、权限码）由 `macmini` 维护；`macbook` 可以校对、提修改，改动前先在群里说明。
- 契约改动当天推到远端，其他机器以远端文档为准实现，避免「口头约定」导致的字段漂移。
- 契约与实现冲突时，先改文档再改代码；生成器的 schema 变更仍由 `macmini` 执行。

## 7. 环境一致性

- macOS 的两台机器都使用 `CMakePresets.json` 里的 `macos-dev` / `macos-release`；Windows 的 `12600k` 使用 `windows-dev` / `windows-release`，不各自发明构建参数。
- `XIAOTU_BUILD_SHELL` 只控制 macOS 壳，Windows 侧 preset 保持 `OFF`；Windows 壳在 `shell/win/` 独立工程里构建（见该目录 README），不走 preset。
- 依赖版本：`vcpkg.json` 声明依赖，未安装 vcpkg 时回落到 `third_party/` 内嵌头文件。
- **不同步**：`build/`、`~/.ccache`（或 `.ccache/`）、`.vcpkg-cache/`、`tools/codegen/.venv/`。这些是机器本地缓存，各机器各自编译，避免架构/路径不一致导致的怪问题。
- vcpkg 的 `builtin-baseline` 用于锁定依赖版本；**当前仓库尚未写入 baseline**。在补上之前，以 `third_party/` 内嵌头为准，各机器不要一方启用 vcpkg、另一方用内嵌版本做对比测试。补齐 baseline 属于构建体系变更，按第 2 节由 `macmini` 执行并通知另外两台。

## 8. 夜间任务（仅 `macmini`）

- 入口：`tools/nightly/nightly.sh`，launchd 模板：`tools/nightly/com.simem.xiaotu.nightly.plist`，安装步骤见 `tools/nightly/README.md`。
- 内容：全量构建 → ctest → ASan/UBSan 构建与测试（独立 `build/asan`）→ clang-tidy（缺失时 cppcheck）扫描 → 日志按日期落盘。
- 失败通知通过 `XIAOTU_NIGHTLY_WEBHOOK` 配置；未配置时只写日志，不打扰。
- 脚本只提供模板，**不在仓库里自动加载 launchd**；是否启用由 `macmini` 手动决定。

## 9. 常用命令速查

```bash
# 开工
git switch main && git pull --rebase origin main

# 新建任务分支（每台用自己的前缀）
git switch -c 12600k/win-shell

# macOS：构建 + 测试（发布态）
cmake --preset macos-release && cmake --build --preset release
ctest --test-dir build/release --output-on-failure

# Windows：构建 + 测试（发布态）
cmake --preset windows-release && cmake --build --preset windows-release
ctest --test-dir build/windows --output-on-failure

# 开发态（改前端）
cmake --preset macos-dev && cmake --build --preset dev
cmake --preset windows-dev && cmake --build --preset windows-dev

# 收工
git add -A && git commit -m "feat: …" && git push -u origin HEAD

# 合并前（已推送的提交不改写历史）
git fetch origin && git merge origin/main

# 清理已合并分支
git push origin --delete <分支名> && git branch -d <分支名> && git fetch --prune
```

# 版本策略

## 唯一来源

产品版本只写在仓库根 `VERSION` 一处，CMake 读取后注入 `PROJECT_VERSION` 与 `XIAOTU_VERSION`；`Info.plist` 用 `@PROJECT_VERSION@`，Windows 安装器由 CI 用 `/DAppVersion` 传入。发版只改 `VERSION`，不要在各处手写版本号。

## 0.x 阶段（已结束，上一版 0.9.0）

- 允许接口与数据表变动，不承诺向后兼容。
- 迁移器保证旧库升得上去；破坏性改动必须配迁移与升级测试。
- 版本号按数字段比较，`0.9.0 < 0.10.0`，禁止字符串比较。

## 1.0 阶段（当前）

- 进入稳定期，破坏性变更必须走废弃 + 提前公告（至少一个 MINOR 周期）。
- API schema 版本严格递增，`/api/health` 返回的 `api_version` 只接受当前与 N-1，其余返回 426。
- 迁移脚本一经发布不得修改，启动时校验 checksum。

## 升到 1.0 的门槛（已达成，2026-11-17）

同时满足才发 1.0：

1. 至少两三家真实客户稳定使用满一个月；
2. 无 P0 问题；
3. API 连续两个版本没有破坏性改动。
