## 5. 发布过程发现的问题与处置

### 5.1 首包漏传更新配置（发布前拦截，已重打）

第一遍 `package_macos.sh` 未传 `XIAOTU_UPDATE_MANIFEST_URL / FEED_URL / PUBKEY` 三参数，
产出包「更新配置：未配置（更新功能关闭）」——若上线，1.0.17 用户将无法收到后续应用内更新。
**处置**：按 `publish_macos.sh` 尾部提示的标准参数值重打并重新公证，终包确认「更新配置：已注入」。
**教训**：发布出包必须显式带三参数（脚本会打印下次该传什么），完成日志里
「更新配置」一行必须核对，不能只看「公证通过」。

### 5.2 NOTES_ONLY 测试用例时序缺陷（已修复 `1571cec`）

`test_release_scripts.py` 的用例用仓库 VERSION.txt 做 NOTES_VERSION，而脚本守卫要求
与线上清单版本一致——发布前窗口（版本已 bump、清单未更新）必然误报失败。
**处置**：用例改为拉线上清单取统一版本，与发版时序解耦；重跑全绿。
脚本的守卫行为本身正确（补发说明页必须版本匹配）。

### 5.3 Gitee API 核验两个坑（非发布问题）

- 私有仓库匿名 API 返回 `Not Found Project`、网页 403——核验必须带 `access_token`。
- `releases/tags/v1.0.17%2B13` 路径接口对 tag 中的 `+` 编码识别有怪癖返回空——
  改用 `releases` 列表接口过滤确认。
