# 前端交接：更新模块（macbook → macmini）

> 历史归档：本文是当时的交接快照，命令、路径与代码基准可能已过时，勿照做；当前实现与发布方式见 `README.md` 与 [更新模块技术方案](更新模块技术方案.md)。
>
> **P3 起状态契约已统一**（见 [更新模块拆分重构方案](更新模块拆分重构方案.md) §2.4）：
> 两壳回调的 `status` 为引擎统一 `status_json`（`state`/`manifest_*`/`bytes_done`/
> `bytes_total`/`pending_path`/`next_check_epoch`/`consecutive_failures` 等 30 字段），
> mac 另带平台扩展键（`install_engine`/`prefetch_state`/`previous`/`recovery_required`/
> `intermediate` 等）；下第 3 节的旧键名（`pending_version`/`prefetch_bytes`/
> `next_check_at` 等）由 `web/app.js` 的 `normalizeUpdateStatus` 归一，壳侧不再输出。

- 代码基准：`main` @ `8a3f09c`
- 对照文档：[更新模块技术方案](更新模块技术方案.md)、[部署说明](../deploy/README.md)
- 本文只描述前端与桥接层的契约；服务端接口 `GET /api/update/check` 已实现，桌面原生的更新预检查、后台预下载与恢复回退桥方法均已实现，桌面端更新卡片也已接入。网络版另在「关于与诊断」页提供「软件更新」卡片（`GET /api/update/status`、`POST /api/update/download`、`POST /api/update/download/cancel`、`POST /api/update/install`），与下面的原生桥方法不是同一条链路。
- 不确定项已明确标注。

## 1. 职责划分

| 能力 | 归属 | 文件 | 当前状态 |
| --- | --- | --- | --- |
| 清单拉取与验签、版本/兼容/灰度判定、跳过、失败计数、Sparkle 触发 | macbook | `shell/mac/updater.{h,mm}` | 已实现 |
| 五个 message handler 注册、参数校验、回调 JS | macbook | `shell/mac/webview.mm` | 已实现 |
| 设置页入口、更新弹窗、强制阻断、错误文案 | macmini | `web/app.js`（及样式） | 已实现（含强制升级阻塞提示、重新下载大小与截止时间展示） |
| 网络版服务端检查接口 | macbook | `server/src/update_service.cpp`、`http_server.cpp` | 已实现，本次不涉及 |

约定：macbook 只提供桥方法与状态数据，不写任何业务界面；macmini 只消费桥方法，不直接调用原生对象。

桥接沿用现有模式（见 `xiaotuPrintPdf`）：JS 通过
`window.webkit.messageHandlers.<name>.postMessage(payload)` 发起，原生通过
`webview.evaluateJavaScript("window.<callback>(...)" )` 异步回调。**不存在同步返回值**；前端应封装为 Promise。

## 2. 桥方法契约

以下五个 handler 名称与参数为本次约定，已在 `webview.mm` 注册；`XiaotuUpdater` 提供
`checkNowWithCompletion:`、`skipVersion:days:completion:`、`installUpdateWithCompletion:`、
`resumeWithCompletion:`，内部共享同一条检查链路。所有回调都在主线程异步触发。

### 2.1 `xiaotuUpdateCheckNow`

- 请求：`postMessage({})`，无参数。
- 行为：立即执行一次清单检查（绕过 24h 定时，不绕过暂停状态与跳过规则）。
- 回调：`window.xiaotuUpdateCheckDone(result)`
  - `result.ok`：`boolean`
  - `result.code`：`string`，成功为 `"CHECKED"`；失败为 `"CHECK_FAILED"`、`"COOLDOWN"`、`"NOT_CONFIGURED"`、`"PAUSED"` 之一
  - `result.update_available`：`boolean`
  - `result.last_result`：`string`，与 `status.last_result` 一致，便于区分“成功但无更新 / 跳过 / 不兼容”
  - `result.retry_after`：`number`，仅 `code="COOLDOWN"` 时出现，单位秒
  - `result.status`：状态字典（见第 3 节），失败时也返回当前状态
- 频次：手动检查建议 1 分钟冷却，冷却内返回 `code="COOLDOWN"`，前端把按钮置灰并显示剩余时间；自动检查不受冷却影响。
- 失败表达：不抛异常，用 `ok=false` + `code`；网络错误统一为 `CHECK_FAILED`，具体原因写日志，不向用户暴露。

### 2.2 `xiaotuUpdateStatus`

- 请求：`postMessage({})`。
- 回调：`window.xiaotuUpdateStatusDone(status)`
  - 返回第 3 节的状态字典；未配置清单时仍返回对象，`enabled=false`。
- 频次：只读，无限制；建议页面进入与弹窗打开时各取一次。

### 2.3 `xiaotuUpdateSkip(version, days)`

- 请求：`postMessage({version: string, days: number})`
- 参数：
  - `version`：必填，要跳过的版本号（来自更新判定结果，如 `"1.4.2"`），空字符串视为无效。
  - `days`：可选，默认 `7`，允许 `1–30` 的整数；超出范围返回参数错误。
- 回调：`window.xiaotuUpdateSkipDone(result)`
  - `ok`：`boolean`
  - `code`：`"SKIPPED"` / `"INVALID_ARGUMENT"` / `"MANDATORY_UPDATE"`（安全等强制更新不允许跳过）
  - `status`：更新后的状态字典
- 语义：仅对当前版本生效；到期后自动恢复提示，无需额外清理。

### 2.4 `xiaotuUpdateInstall`

- 请求：`postMessage({})`。
- 行为：用户主动点“立即更新”时调用。有 Sparkle 时打开 Sparkle 的标准更新界面或触发下载安装；无 Sparkle（本机开发构建）时返回不可用。
- 回调：`window.xiaotuUpdateInstallDone(result)`
  - `ok`：`boolean`
  - `code`：`"STARTED"` / `"UNAVAILABLE"` / `"NO_PENDING_UPDATE"`
  - `message`：可选，仅用于日志，不建议直接展示
- 说明：强制更新场景下也应走该入口，由 Sparkle 完成下载、验签、替换；前端不自行下载安装包。
- 失败表达：`UNAVAILABLE` 时前端提示“当前版本不支持自动安装，请前往下载页”，并给出 `SUFeedURL` 对应的下载页地址（OSS 已配，见 `发行与安装说明.md`）。

### 2.5 `xiaotuUpdateResume`

- 请求：`postMessage({})`。
- 行为：清除“连续 3 次启动失败”的暂停标记与失败计数（`launch_attempts` 归零），并立即触发一次自动检查、重新安排 24h 调度；未配置清单时只清除标记，不发起检查。
- 回调：`window.xiaotuUpdateResumeDone(result)`
  - `ok`：`boolean`，恢复成功与“本来就没暂停”都为 `true`
  - `code`：`"RESUMED"` / `"NOT_PAUSED"`
  - `status`：更新后的状态字典
- 边界：
  - `NOT_PAUSED` 是幂等结果，不是错误；前端可直接把按钮恢复为不可用或隐藏。
  - 不受 1 分钟手动冷却限制（它不是手动检查），但会更新 `last_check_at` 与 `last_result`。
  - 恢复不会重试上一次失败的安装，只恢复检查调度。
  - 同时清除恢复模式标记（`recovery_required=false`），但保留旧版本副本，等待稳定启动 3 次后自动清理。

### 2.6 `xiaotuUpdateRollback`

- 请求：`postMessage({})`。
- 行为：仅在恢复模式（`status.recovery_required=true`）且存在旧版本副本时可用。原生退出程序，由脚本等待进程结束后用安装前保留的 `.app` 替换当前版本并重新启动。
- 回调：`window.xiaotuUpdateRollbackDone(result)`
  - `ok`：`boolean`
  - `code`：`"ROLLING_BACK"` / `"NOT_RECOVERY"` / `"NO_PREVIOUS"` / `"FAILED"`
  - `message`：可选，可直接展示失败原因
- 说明：回退只替换程序，不自动恢复数据库。若升级包含 schema 变更，需先用 `backups/app-*-pre-v*.db` 恢复升级前数据；前端必须在确认框里说明这一点。

### 2.7 `xiaotuUpdateOpenBackupFolder`

- 请求：`postMessage({})`。
- 行为：在 Finder 中打开服务端备份目录（`~/Library/Application Support/com.simem.xiaotu/backups`），便于用户找到升级前备份。
- 回调：`window.xiaotuUpdateOpenBackupFolderDone(result)`
  - `ok`：`boolean`
  - `code`：`"OPENED"` / `"NOT_FOUND"` / `"FAILED"`
  - `message`：可选，可直接展示

## 3. 状态字典

`XiaotuUpdater.status` 实际返回：

| 字段 | 类型 | 含义 | 取值/边界 | 前端用途 |
| --- | --- | --- | --- | --- |
| `enabled` | bool | 是否配置了清单地址 | `false` 表示 `XiaotuUpdateManifestURL` 为空，更新功能关闭 | 可直接展示（“自动更新未启用”） |
| `channel` | string | 当前通道 | `"stable"` / `"beta"` | 可直接展示 |
| `next_check_at` | double | 下次计划检查时间，UTC 秒 | `0` 表示尚未安排；检查失败时按 1 分钟 / 10 分钟 / 1 小时退避重排 | 可格式化展示；`0` 时不显示 |
| `check_failures` | int | 连续检查失败次数 | 任意一次成功即清零 | 诊断展示（“已连续失败 N 次，正在退避重试”） |
| `launch_attempts` | int | 连续启动未稳定的次数 | `0–3`，稳定运行 30 秒后清零 | 仅内部判断，不直接展示 |
| `paused` | bool | 是否因连续启动失败暂停自动更新 | `true` 时不再自动检查 | 可展示为“自动更新已暂停”，并提供恢复入口 |
| `recovery_required` | bool | 是否进入恢复模式 | 连续 3 次启动未稳定，且处于新版本验证期或仍有待装版本 | `true` 时展示恢复引导与回退入口 |
| `previous` | object | 安装前保留的旧版本副本 | `{available: bool, version: string 或 null, build: int}` | `available=true` 时提供“回退到上一版本” |
| `skipped_version` | string 或 null | 已跳过的版本 | `null` 表示未跳过 | 可直接展示（“已跳过 1.4.2”） |
| `skip_until` | double | 跳过截止时间，UTC 秒 | `0` 或已过期表示不再生效 | 展示“至 2026-11-20” |
| `last_check_at` | double | 上次检查时间（自动或手动，成功或失败均更新），UTC 秒 | `0` 表示从未检查；持久化，重启后仍有效 | 展示“上次检查：…” |
| `last_result` | string 或 null | 上次检查结论 | `NO_UPDATE` / `UPDATE_AVAILABLE` / `SKIPPED` / `INTERMEDIATE_REQUIRED` / `INCOMPATIBLE_SCHEMA` / `OS_UNSUPPORTED` / `INCOMPATIBLE_API` / `NOT_IN_ROLLOUT` / `CHECK_FAILED` / `PAUSED` / `NOT_CONFIGURED`；从未检查为 `null` | 设置页静态说明，不弹窗 |
| `pending_version` | string 或 null | 待安装版本号 | `null` 表示没有 | 提示条标题 |
| `pending_build` | int | 待安装构建号 | 两平台都是发布构建号（`build = seq`）；旧清单可能为 `0`，此时界面只显示版本号 | 仅内部判断；为 `0` 时界面只显示版本号 |
| `pending_size` | int | 待安装安装包大小（字节） | `0` 表示清单未给出 | 安装前提示“将重新下载约 X MB” |
| `pending_deadline` | string 或 null | 清单 `mandatory_deadline`，ISO 8601 UTC | `null` 表示未声明、立即强制；有值时到期才强制（宽限期） | 展示“请于 … 前完成升级，到期后无法跳过” |
| `update_available` | bool | 是否有待安装版本 | macOS 用 `pending_version > 当前版本` 判定，Windows 用 `pending_build > 当前构建号` | 控制提示条/红点，不自动弹窗 |
| `mandatory` | bool | 待安装版本是否强制 | 仅 `update_available=true` 时可真 | 决定是否阻断 |
| `reason` | string 或 null | 强制原因或不兼容结论 | 强制时为 `SECURITY` / `PROTOCOL` / `REGULATORY` / `MIN_SUPPORTED`；最近一次结论为 `INCOMPATIBLE_SCHEMA` 且无强制待更新时为 `INCOMPATIBLE_SCHEMA`；其余为 `null` | 强制弹窗文案 / 不兼容说明 |
| `min_supported_version` | string 或 null | 服务端轻量握手要求的最低客户端版本 | 来自 `/api/health`；未配置或从未握手为 `null` | 诊断展示；启动时由壳直接阻断，不依赖此字段 |
| `release_notes_url` | string 或 null | 待安装版本的说明页 | 来自清单，可空 | “查看详情”按钮 |
| `intermediate` | object 或 null | 中间版本信息 | 单机版已解析清单 `upgrade_path`；本地 schema 低于 `schema_min` 且能选出步骤时为 `{version, build, schema}`，否则 `null` | 非 null 时展示中间版本文案与下载入口 |

说明：

- `pending_*` 只在检查结论为 `UPDATE_AVAILABLE` 时写入；检查到已是最新、平台/通道不匹配、`min_os` 过低、API 不在区间、schema 不兼容、灰度未命中或处于跳过期时会被清空。
- `intermediate` 与 `pending_*` 互斥：本地 schema 低于 `schema_min` 时不会产生“待安装最新版”，只给出中间版本；选不出步骤时 `intermediate=null`、`last_result=INCOMPATIBLE_SCHEMA`、`reason=INCOMPATIBLE_SCHEMA`。
- 单机版与网络版使用同一个 `select_intermediate_step`（`core/src/update.cpp`）选中间版本，规则为“schema 严格大于本地值且最接近的一步”，两边结果一致。
- `update_available`、`pending_version`、`mandatory` 均可直接由 `status` 驱动界面；`checkNow` 的回调里也带同一份 `status`，两者不冲突。
- 用户执行跳过时，待更新记录会被清空，`last_result` 置为 `SKIPPED`，因此不会再触发提示条。

## 4. 交互场景与文案

### 4.1 有可选更新

- 形式：非模态提示条或设置页红点，不阻断操作；主界面不自动弹窗。
- 文案：“发现新版本 1.4.2，包含问题修复与改进。”
- 按钮：“查看详情”（打开 `release_notes_url`）、“立即更新”、“跳过此版本”。
- “立即更新”调用 `xiaotuUpdateInstall`；若 `UNAVAILABLE`，改为“前往下载”。

### 4.2 强制更新

- 范围仅四类：安全漏洞、schema/协议不兼容、法规税控截止、低于服务端最低支持版本。
- 阻断程度：登录后若壳内 `status.mandatory=true` 且强制已生效（`mandatoryActive()`：未设期限或 `now >= mandatory_deadline`），弹出不可关闭的阻塞提示（Esc 与点遮罩无效），只保留“立即安装”；不提供“跳过此版本”。
- 宽限期：设了 `mandatory_deadline` 时，截止前按普通更新提示（可稍后、可关闭），文案为“计划升级：… 请在 … 前完成升级，到期后将无法跳过”；到期后同一版本自动转为阻塞提示，无需重新发布清单。期限解析失败按已到期处理。
- 文案：“当前版本必须升级（安全漏洞修复）：1.4.2（构建 …）。安装时会重新下载约 X MB 并退出程序，升级后才能继续使用。”
- 安装前提示：Sparkle 安装会下载并校验安装包，界面按 `status.pending_size` 显示预计大小；Sparkle 构建（`install_engine=sparkle`）不再展示后台预下载与「下载并校验」入口。
- 未处理后果：每次启动都会再次提示，且不提供“跳过”；关闭窗口即退出应用。
- 低于服务端最低支持版本时，壳在启动加载页面阶段直接展示“必须升级”阻塞页（`min_supported_version`），不进入业务界面。
- 注意：服务端 `MIN_SUPPORTED` 与清单 `mandatory` 都会产生强制标记；安全更新不受 7 天跳过限制。

### 4.3 中间版本（`INTERMEDIATE_REQUIRED`）

- 来源：
  - 网络版：`/api/update/check` 返回 `code=INTERMEDIATE_REQUIRED`、`intermediate.version/build/schema`；
  - 单机版：`status.intermediate` 同名字段，由原生从清单 `upgrade_path` 选出，选择规则与网络版共用 `select_intermediate_step`。
- 文案：“当前数据版本较旧，请先升级到 1.3.5，再升级到最新版。”
- 操作：仅提供“前往下载 1.3.5”；**不支持一键跳转安装**（Sparkle 清单只覆盖最新版，中间版本需要单独安装包，是否提供由发布侧决定，标注不确定）。
- 不展示“跳过”。
- 若 `intermediate=null` 且 `last_result=INCOMPATIBLE_SCHEMA`，说明本地数据版本过旧而清单未给出可用中间版本：不展示下载入口，提示联系技术支持。

### 4.4 跳过版本

- 入口：可选更新弹窗/提示条中的“跳过此版本”，调用 `xiaotuUpdateSkip(version, 7)`。
- 到期：7 天后下次检查会重新提示，无需额外提醒；设置页可显示“已跳过 1.4.2，至 2026-11-20”。
- 安全更新：按钮隐藏或点击后返回 `MANDATORY_UPDATE`，文案：“此更新包含安全修复，不能跳过。”

### 4.5 连续 3 次启动失败（恢复模式）

- 触发：`launch_attempts >= 3`，且满足「新版本验证期（安装后的新版本；macOS 按版本号、Windows 按 build）」或「仍有更高待装版本」，`recovery_required=true`、`paused=true`。
- 告知：更新卡片展示恢复模式横幅：“当前版本连续 3 次启动未稳定，自动检查已暂停。”
- 回退：存在旧版本副本时提供“回退到上一版本”，调用 `xiaotuUpdateRollback`；原生退出、替换 `.app` 并重新启动旧版本。确认框必须提示：若数据库结构已升级，需先恢复升级前备份。
- 继续：提供“继续使用当前版本”，调用 `xiaotuUpdateResume`；清除暂停与恢复标记、失败计数归零，旧版本副本在稳定启动 3 次后自动删除。
- 辅助：提供“打开备份目录”，调用 `xiaotuUpdateOpenBackupFolder`，便于找到 `backups/app-*-pre-v*.db`。
- 无副本：`previous.available=false` 时隐藏回退按钮，文案改为“请从官网重新下载上一版本安装包”。
- 按钮边界：`status.paused=true` 时展示恢复入口；调用返回 `NOT_PAUSED` 说明已被自动恢复或重复点击，前端隐藏入口即可，不提示错误。

### 4.6 不打扰的分界

以下情况**不弹窗、不提示**，只在设置页“关于/更新”中展示状态：

- 无更新（`NO_UPDATE`）；
- 更新源未配置（`UPDATE_NOT_CONFIGURED` / `enabled=false`）；
- 验签失败、验签工具不可用、清单损坏（服务端/客户端均只记录日志）；
- 不在灰度范围（`NOT_IN_ROLLOUT`）；
- 系统版本低于清单 `min_os`（`OS_UNSUPPORTED`）或 API 不在清单区间（`INCOMPATIBLE_API`）；
- 检查失败（网络错误、超时）。

## 5. 错误码到用户提示

| 错误码 | 用户可见文案 | 是否记录/上报 |
| --- | --- | --- |
| `UPDATE_NOT_CONFIGURED` | “当前版本未启用自动更新。”（设置页静态说明，不弹窗） | 记录日志 |
| `UPDATE_UNVERIFIED` | “更新服务暂时不可用，请稍后再试。”（不暴露“未验签”） | 记录日志，建议上报 |
| `UPDATE_VERIFY_UNAVAILABLE` | “更新服务暂时不可用，请稍后再试。” | 记录日志，建议上报 |
| `UPDATE_SIGNATURE_INVALID` | “更新包校验失败，已停止本次更新。请联系技术支持。” | 记录日志，建议上报 |
| `MANIFEST_UPGRADE_PATH_INVALID` | “更新信息配置有误，请稍后再试。” | 记录日志，建议上报 |
| `INTERMEDIATE_REQUIRED` | “请先升级到 1.3.5，再升级到最新版。” | 记录日志 |
| `INCOMPATIBLE_SCHEMA` | “当前版本与更新包不兼容，请联系技术支持。” | 记录日志，建议上报 |

说明：错误码来自网络版接口或原生判定；桌面单机版不会出现服务端错误码，但可能因清单不可用走 `CHECK_FAILED`，文案统一为“检查更新失败，请稍后再试”。

## 6. 验收点

以下均需在真实 `.app` 中手工验证：

1. 未配置 `XiaotuUpdateManifestURL`：启动无错误弹窗，设置页显示“自动更新未启用”，`status.enabled=false`。
2. 配置测试清单并放新版本：24 小时内首次启动出现非模态提示；点击“跳过此版本”后 7 天内不再提示（可通过修改系统时间或把跳过天数设为 1 验证）。
3. 强制更新：重启后无法进入主界面，仅“立即更新/导出/退出”可用；“跳过”入口不存在。
4. 中间版本：用 schema 低于 `schema_min` 的数据库请求，`status.intermediate.version` 应与清单 `upgrade_path` 选出的版本一致，且不显示“跳过”。
5. 连续 3 次启动失败：模拟待更新版本后连续启动（不等待稳定 30 秒），第 3 次启动出现暂停提示；点击“恢复自动更新”后 `paused=false`、`launch_attempts=0`。
6. 验签失败：篡改清单后请求，界面只显示“更新服务暂时不可用”，不出现“有新版本”。
7. 冷却：连续点击“检查更新”，第二次返回 `COOLDOWN` 且按钮置灰。
8. 无网：断网后手动检查，提示“检查更新失败”，不崩溃、不弹强制更新。
9. `xiaotuUpdateInstall` 在无 Sparkle 构建中返回 `UNAVAILABLE`，前端降级为下载页提示。

### 6.1 已自动化覆盖（`ctest -R update_smoke`）

原生层没有 XCTest 工程，桥接中用到的判定已抽到 `core/src/update.cpp` 的纯函数并由
`tests/update_smoke.cpp` 覆盖：

- 手动检查冷却：从未检查放行、冷却内返回剩余秒数、到期放行、时钟回拨不阻塞；
- 跳过天数：1 与 30 合法，0、31、负数拒绝；
- `install` 判定：无 Sparkle → `UNAVAILABLE`（无论有无待更新）、有 Sparkle 但无待更新或
  待更新不大于当前构建 → `NO_PENDING_UPDATE`、其余 → `STARTED`；
- 中间版本选择：最接近的更大 schema、schema 相等时跳过、无更大值/空路径返回空；
  并逐值比对 `evaluate_manifest` 与 `select_intermediate_step` 的结果一致；
- `resume` 判定：`paused=true → RESUMED`、`paused=false → NOT_PAUSED`。

参数类型（`version` 非字符串、`days` 非数字或非整数）由 `webview.mm`/`updater.mm` 运行时校验，
无法脱离 GUI 自动化，按 6.2 手工验证。

### 6.2 仍需真机手工验证

- 第 1–9 条的界面表现（提示条、强制阻断、按钮置灰、文案）已在 `web/app.js` 实现；强制拦截、重新下载提示、`min_supported_version` 阻断与截止时间展示已真机验证。
- 发布构建默认内置 `third_party/sparkle/Sparkle.framework`：`status.install_engine="sparkle"`，
  `install` / `download` 应返回 `STARTED` 并唤起 Sparkle 下载与安装界面；
  仅未链接 Sparkle 的开发构建才会走 `UNAVAILABLE` / `OPENED` 分支。
- `last_check_at` 持久化：手动检查一次 → 记录 `status.last_check_at` → 退出并重启 →
  `status.last_check_at` 应保持不变且非 0。
- 冷却：连续调用两次 `xiaotuUpdateCheckNow`，第二次应返回 `COOLDOWN` 且 `retry_after <= 60`；
  等 10 分钟后再次调用应返回 `CHECKED`。
- 参数校验：`postMessage({version: "", days: 7})`、`{version: "1.4.2", days: 0}`、
  `{version: "1.4.2", days: 7.5}` 均应返回 `INVALID_ARGUMENT` 且带 `status`。
- 单机版中间版本：构造 `schema_min` 高于本地 schema、且清单带 `upgrade_path` 的环境，
  检查一次后 `status.intermediate` 应为 `{version, build, schema}`，`last_result=INTERMEDIATE_REQUIRED`；
  删除 `upgrade_path` 后重查，应变为 `intermediate=null`、`last_result=INCOMPATIBLE_SCHEMA`、`reason=INCOMPATIBLE_SCHEMA`。
- 暂停与恢复：构造 `paused=true` 后调用 `xiaotuUpdateResume`，应返回 `RESUMED`，
  `status.paused=false`、`launch_attempts=0`，且 `last_check_at` 在随后一次自动检查后更新；
  再次调用应返回 `NOT_PAUSED`。

## 7. 前置依赖

发布包不再手工改 `shell/mac/Info.plist`：`tools/package/package_macos.sh` 在打包时通过 CMake 变量注入三项，并回读校验；仓库内的 `Info.plist` 保持空占位。

- `XiaotuUpdateManifestURL`：自研检查读取的 `manifest.json`（v2）地址；
- `SUFeedURL`：Sparkle appcast 地址；
- `SUPublicEDKey`：Ed25519 公钥（base64），清单验签与 Sparkle appcast 验签共用。

出包时同时提供 `XIAOTU_UPDATE_MANIFEST_URL`、`XIAOTU_UPDATE_FEED_URL`、`XIAOTU_UPDATE_PUBKEY` 三项（必须同时给或同时留空）。`SUEnableAutomaticChecks=false`（定时检查由自研层负责），`SUAutomaticallyUpdate=false`、`SUAllowsAutomaticUpdates=false`（不做静默安装，后台预下载由自研链路负责）。

未配置时：

- 原生层记录“未配置清单地址，自动检查关闭”，`status.enabled=false`；
- 前端应表现为“未配置自动更新”，**不得弹错误框或提示验签失败**；
- “立即更新”按钮应置灰或隐藏。

发布前还需在 `SUFeedURL` 指向的目录放置 appcast 与安装包，否则 Sparkle 会失败；该部分由 `tools/release/publish_macos.sh` 负责，不在前端范围。

## 8. 安全边界：单机版清单验签

单机版（`shell/mac/updater.mm`）拉取 `XiaotuUpdateManifestURL` 后，先用 `Info.plist` 的 `SUPublicEDKey` 对清单做 Ed25519 验签（`xiaotu::verify_manifest_signature`）；验签失败记 `CHECK_FAILED` 并中止，不做版本比较、不提示、不触发 Sparkle。未链接 OpenSSL 的构建会跳过 C++ 侧验签，由 Sparkle 在用户点「安装更新」时校验 appcast；发布构建应保持验签开启。

边界说明：

- 即使清单通过验签，也只影响提示层：显示哪个版本、说明页地址与是否需要中间版本；不会因此自动下载或安装。
- 实际安装由 Sparkle 完成：appcast 与安装包使用 `SUPublicEDKey` 做 Ed25519 校验，安装包还要通过 macOS 代码签名/公证校验；校验失败时 Sparkle 中止，不会替换当前应用。
- 因此伪造清单无法达成“投递并运行任意代码”。前端不应把清单内容当作可信来源去索取敏感信息（如凭据）。
- 网络版 `/api/update/check` 在服务端验签；本节只描述单机版直连厂商清单的路径，两者不是同一条链路。
