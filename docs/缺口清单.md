- 判定依据：全仓库检索 `Sparkle`、`appcast`、`SUFeedURL` 均无实现代码；`/api/health` 也无版本/更新字段。
- 依赖决策：Q23 检查频率与匿名统计、Q24 beta 与灰度、Q25 强制升级与静默安装、Q26 Windows 更新方式。

### 1.2 前端离线与草稿保护（技术方案 6.3）

- 缺口：无断网提示、无请求超时统一处理、无重试、无会话草稿持久化；断网时仅表现为请求失败。
- 代码位置：`web/app.js`（无 `navigator.onLine`、`sessionStorage`/`localStorage` 相关逻辑）、`web/styles.css`（无离线态样式）。
- 判定依据：检索 `onLine`、`offline`、`sessionStorage` 无命中。
- 备注：`web/app.js` 属三文件约束中的禁区，实施前需与主线排他。

### 1.3 单据幂等与乐观锁（技术方案 6.2、5.3）

- 缺口：`doc_header` 无 `request_id`，保存单据不幂等；无 `version` 字段，编辑/审核无乐观锁；并发下依赖状态判断与事务，重复提交可能产生两张单据。
- 代码位置：`core/src/migrations.cpp`（`doc_header` 定义，第 49–64 行；后续 `ALTER` 未增加上述列）、`core/src/document.cpp`（保存与审核入口，无幂等键处理）。
- 判定依据：全仓库检索 `request_id` 无业务实现；`doc_header` 无 `version` 列。
- 影响：网络版多人同时操作时风险高于单机版。

### 1.4 恢复向导与恢复审计（技术方案 6.5、4.7）

- 缺口：恢复仅支持 CLI `--restore`，无界面选择备份、无恢复前确认与结果展示；恢复成功后未写 `audit_log`。
- 代码位置：`server/src/cli_main.cpp`（`--restore` 分支）、`core/src/backup.cpp`（`restore_database` 无审计写入）、`web/app.js`（无备份/恢复页面）。
- 判定依据：`backup.cpp` 检索 `RESTORE` 无审计写入；前端无对应入口。
- 备注：恢复需停服，向导若做也应以“下载/指引 + CLI”或独立维护工具为主。

### 1.5 主体变更迁移工具（技术方案 7.4）

- 缺口：无 bundle id 不变情况下的数据目录迁移脚本、无 Team 变更后的迁移指引工具。
- 代码位置：无对应实现，仅有文档方案。
- 判定依据：`tools/` 下无迁移脚本；`shell/mac/Info.plist` 固定 `com.simem.xiaotu`。
- 依赖决策：Q20–Q22 发布主体、发票、软著。

### 1.6 强制改密与登录失败锁定（技术方案 5.7、4.7）

- 缺口：`app_user` 无 `must_change_password`、`failed_count`、`locked_until`；登录失败仅记录审计，不累计、不锁定。

## 二、部分实现

### 2.1 客户/供应商统一收口（技术方案 4.1、5.2）

- 现状：`partner` 表已建并完成 v28 1:1 迁移（含 `partner_legacy_map`），`doc_header` 已有 `partner_id`。
- 缺口：销售单据与信用额度仍读写旧 `customer` 表；供应商写 `partner_id`，客户仍写 `customer_id`，两套主数据并存。
- 代码位置：`core/src/document.cpp` 第 464–471 行（信用额度查 `customer.credit_limit_cents`）、第 732–733 行（供应商写 `partner_id`、客户写 `customer_id`）；`core/src/migrations.cpp` 第 824–852 行（`partner` 表）。
- 判定依据：`partner` 表已有 `credit_limit_cents`，但信用校验未使用；客户侧新增数据仍进 `customer`。
- 风险：新建客户可能不在 `partner` 中，后续统一时需二次迁移；信用额度口径可能分裂。

### 2.2 成本重算只读（技术方案 4.4）

- 缺口：成本重算只做核对与差异展示，不回写结存与流水。
- 代码位置：`core/include/xiaotu/cost_recalc.h` 第 33–35 行（结果仅作核对输出）、成本重算路由仅返回差异。
- 判定依据：接口与注释均标注“只读核对”；无写回事务。
- 依赖决策：Q11 含税成本口径确定后再做写回，避免返工。

### 2.3 报表导出非流式（技术方案 4.6）

- 缺口：导出一次性取最多 100000 行并在内存生成 XLSX/CSV，不是流式写出；超限截断。
- 代码位置：`server/src/report_routes.cpp` 第 660、1051、1163 行（`filter.limit = 100000`）。
- 判定依据：导出接口存在固定上限，超限时在提示中标注“单次上限 100000 行”。

### 2.4 用户与审计模型（技术方案 5.7、4.7）

- 缺口：用户仅单角色（`role_id`），无多角色；`audit_log` 仅 `at/actor/action/entity/entity_id/entity_no/detail`，无 `client_ip`、`request_id`、`detail_json`。
- 代码位置：`core/src/migrations.cpp` 第 245–254 行（`audit_log`）、`app_user` 定义（单 `role_id`）。
- 判定依据：表结构即为现状；无多角色关联表。
- 备注：是否需要多角色取决于实际客户规模，可与 Q17 一并决定。

### 2.5 版本能力控制（技术方案 6.9）

- 现状：仅 `system.user` 与 `max_users` 生效。
- 缺口：`hidden` 能力、单据数、仓库数等额度未执行；无前端能力派生文件，界面不做能力隐藏。
- 代码位置：`server/src/user_routes.cpp` 第 55、66 行（仅用户数配额）；其余能力未检索到调用点。
- 判定依据：`EditionPolicy` 的配额只在用户创建处使用。

### 2.6 打印能力（技术方案 4.8、6.4）

- 现状：25 个打印目标、模板 CRUD、列配置、桌面 PDF、Cmd+P、方向与连续纸缩放均已实现。
- 缺口：网络版无服务端 PDF 生成/下载，仅支持浏览器打印；页码 `@bottom-right` 在 WKWebView 的兼容性未验证，若无效则 `show_page_no` 实际不生效。
- 代码位置：`server/src/print_routes.cpp`（渲染返回 JSON，不产 PDF）、`web/app.js` 打印视图（页码样式注入）。
- 判定依据：服务端无 PDF 输出接口；页码未做真机/浏览器验证。

### 2.7 打包与分发（技术方案 7.1、7.2）

- 现状：macOS `.app`、图标、`tools/package/make_dmg.sh`、dmg 与 SHA256 已具备；Windows 壳可独立构建。
- 缺口：macOS 仅 ad-hoc 签名，无 Developer ID 与公证；Windows 未接入顶层构建，无安装包、无签名，CI 只编译与跑测试。
- 代码位置：`tools/package/make_dmg.sh`（`codesign --sign -`）、`shell/win/README.md`（声明不接入顶层构建）、`.github/workflows/windows-build.yml`（只 build + test）。
- 判定依据：本机 `security find-identity` 无有效签名身份；CMake 无签名/公证步骤。

### 2.8 同步目录约束（技术方案 7.5）

- 现状：已检测 iCloud/OneDrive 等同步目录并在 `/api/health` 暴露 `data_dir_warning`。
- 缺口：仅告警，不拒绝写入；技术方案写的是“检测到即拒绝”。
- 代码位置：`server/src/http_server.cpp` 第 257 行（`data_dir_warning` 输出）。
- 判定依据：启动流程无拒绝分支。

### 2.9 基础资料物理删除（技术方案 4.1）

- 缺口：删除一律软删，无“无引用时物理删除”。
- 代码位置：`core/src/gen/item_service.cpp` 第 89 行（`soft_delete`），其余主数据生成服务同构。
- 判定依据：服务层无物理删除分支。
- 备注：软删可满足业务，是否补物理删除属产品取舍。

## 三、文档与技术方案不一致（需改代码或改文档，二选一未定）

### 3.1 打印实现模型（技术方案 4.8、5.8、6.4）

- 文档描述：HTML 模板 + `{{}}` 占位符 + 行循环。
- 实际实现：结构化模板（列配置 + 标题/表头/表尾字段），由前端固定渲染，无 HTML 模板引擎。
- 代码位置：`server/src/print_routes.cpp`（模板 CRUD 与 render DTO）、`core/src/print_template.cpp`（列定义与纸型）。
- 判定依据：全仓库无占位符替换逻辑；打印视图由 `web/app.js` 按列配置生成。
- 建议：以实现为准改文档，保留“自定义 HTML 模板”为未来选项。

### 3.2 单据字段表（技术方案 5.3）

- 文档字段：`request_id`、`version`、`remark`、`updated_at`、`source_doc_id` 等。
- 实际：`doc_header` 无上述列；下推通过数量累计实现，不落 `source_doc_id`。
- 代码位置：`core/src/migrations.cpp` 第 49–64 行及后续 `ALTER` 语句。
- 判定依据：表结构与文档字段表不符。
- 建议：若确认需要幂等/乐观锁，按 1.3 补代码并升 v30；否则改文档。

### 3.3 审计与用户字段（技术方案 5.7）

- 文档字段：`client_ip`、`request_id`、`detail_json`、登录失败计数等。
- 实际：`audit_log` 仅 8 列，无 IP/请求号/JSON；用户无锁定字段。
- 代码位置：`core/src/migrations.cpp` 第 245–254 行。
- 建议：与 1.6、2.4 一并决策是补实现还是收敛文档。

### 3.4 权限校验层级（技术方案 6.7）

- 文档描述：权限在服务层强制校验。

- 判定依据：服务层无权限上下文断言。
- 建议：补服务层断言成本低但会重复校验；也可改文档承认“路由层统一入口 + 审查约束”。

### 3.5 打印目标数量（技术方案 4.8）

- 文档：23 个目标。

## 五、建议优先级

### 交付前必须完成

1. **针式打印真机验收与页码方案定稿**（4.8、Q12）：目标客户若使用针式打印机，这是验收硬门槛；页码需先确认 WKWebView 是否支持，再决定 HTML 页脚方案。
2. **软件更新链路**（6.8、Q23–Q26）：至少完成 macOS 侧，否则发布后无法修复线上问题；Windows 可先手动下载过渡。
3. **签名与公证**（7.1、Q20–Q22）：对外分发的前置条件；需先取得 Developer ID 证书。
4. **partner 统一收口**（2.1）：避免新建客户在单据与信用额度上出现两套数据，越晚迁移成本越高。
5. **含税成本口径与成本重算写回**（Q11、2.2）：影响账实一致与毛利报表可信度。
6. **前端离线提示**（6.3）：网络版在断网、休眠、服务重启时缺少可用反馈，属基础体验。
7. **恢复成功审计**（1.4）：恢复是高风险操作，至少保证可追溯，不依赖完整向导。

### 可延后

- 单据幂等与乐观锁（1.3）：单机与小团队风险低；网络版多人并发上量前完成即可。
- 报表导出流式化（2.3）：十万行以内可用，数据规模上来前不阻塞。
- 多单位、批次、数据权限、License、外部对接（Q4、Q5、Q17–Q19）：按目标客户与首发范围决定。
- Windows 安装包与签名（2.7）：若首发仅 macOS，可延后。
- 6.9 其余额度执行（2.5）：当前社区版仅单用户，额度控制优先级低。
- 物理删除与同步目录拒绝写入（2.8、2.9）：软删与告警已可接受。
- 恢复向导 UI（1.4）：CLI 可用时优先保证审计与文档指引。
