- 现状（已完成）：
  - 清单来源：`[update] manifest_url` 优先从厂商更新源拉取（HTTPS），先做结构与 Ed25519 验签，通过后才原子替换 `<data_dir>/updates/manifest/<channel>/manifest.json`（v2 统一清单，按请求平台取 `platforms.*`）；缓存有效期 10 分钟，客户端每次登录检查不会重复访问外网。拉取失败或新清单损坏时回退上一次验签通过的缓存并在状态里标记 `manifest_stale`，无缓存才返回 `UPDATE_MANIFEST_UNREACHABLE`。`[update] manifest_file` 保留给内网/离线部署，每次请求重新读取（`server/src/update_service.cpp` 的 `sync_update_manifest` / `check_for_update`）。两者都未配置时接口返回 `UPDATE_NOT_CONFIGURED` 与「未配置更新清单」，不静默跳过。
  - 清单验签用发布侧同一套 Python 工具；Windows 走 `CreateProcess`、POSIX 走 `fork/execvp`，stdout/stderr 都经管道读回，失败信息带工具最后一行输出（`server/src/process_capture.cpp`；`update_service.cpp` 的 `verify_manifest_signature`）。
  - 新增 `GET /api/update/status`（`setting.read`）返回当前版本/构建/schema、最新版本、发布日期、是否已是最新与失败原因；前端「关于与诊断」页有「软件更新」卡片（`web/app.js` 的 `renderUpdateCard`）。
  - 下载：`POST /api/update/download`（管理员 + `setting.write`）后台用系统 `curl` 下载到 `<数据目录>/updates/`，先比对清单 `size`，再调用验签工具带 `--file` 同时校验清单签名与安装包 sha256；任一失败删除文件并写日志（`server/src/update_install.cpp`）。失败分支已分开：curl 未启动返回 `UPDATE_DOWNLOAD_UNAVAILABLE`，文案「无法启动 curl 下载安装包：…」；已启动但收不到退出状态返回 `UPDATE_DOWNLOAD_FAILED`，文案「下载安装包失败：进程已启动，但无法获取退出状态：…」；正常退出但未生成文件同样判失败，不再用「退出码 0」兜底（`update_install.cpp` 84–112）。
  - 取消与单包清理：`POST /api/update/download/cancel`（管理员 + `setting.write`）置位取消标志并唤醒退避等待，`run_process_capture` 轮询标志后终止 curl（Windows `TerminateProcess` / POSIX `SIGTERM`），下载线程把状态置为 `canceled`、删除半成品且不再自动重试；服务停止时同样中止下载。开始下载前清空目录内其它旧包；后台检查确认已是最新且下载空闲时清空 `<数据目录>/updates/`；同版本包已缓存时删除其余残留。单机版在启动时删除 `done` 状态且待装 build 不高于当前 build 的旧包并回到 idle。
  - 安装：`POST /api/update/install` 必须带 `confirm=true`。服务端复验安装包后按形态定位新程序（单文件可执行程序，或 zip 内与当前程序同名的文件），写入 `updates/staging-*` 并后台启动替换脚本，返回响应后优雅退出；脚本等待进程退出（最多 120 秒），把旧程序备份为 `<程序>.old`、覆盖新程序并按原启动参数与原工作目录重启；覆盖失败时回滚旧版本。`.dmg` 等安装器型包返回 `UPDATE_PACKAGE_UNSUPPORTED`，不会尝试替换（`server/src/update_install.cpp` 的 `stage_update_package` / `schedule_update_replace`，`server/src/http_server.cpp` 的安装路由）。

## 五、建议优先级

### 交付前必须完成

1. **针式打印真机验收**（4.8、Q12）：目标客户若使用针式打印机，这是验收硬门槛；页码方案已定稿（WKWebView 不支持 `@page` margin box 与 `counter(page)`，`show_page_no` 降级为提示性字段），剩套打、走纸、复写三项真机。
2. **软件更新链路**（6.8、Q23–Q26）：服务端检查/下载/验签/打开安装包已通，剩 Sparkle 框架打包、原子替换、回滚与清单托管；否则发布后仍无法自动修复线上问题。
3. **签名与公证**（7.1、Q20–Q22）：对外分发的前置条件；需先取得 Developer ID 证书。
4. **partner 统一收口**（2.1）：避免新建客户在单据与信用额度上出现两套数据，越晚迁移成本越高。
5. **成本调整单**（2.2 的替代路径）：不做重算写回，差异靠成本调整单落地，影响账实一致与毛利报表可信度。
6. **桌面端更新安装**（6.8）：Sparkle 框架打包、用户确认后的原子替换、回滚未接，是启用清单前必须补齐的一环；静默安装按 Q25 不做。
7. **Windows 安装/卸载真机验收**（7.2、Q26）：CI 只保证能编出安装包（未配置证书时未签名），安装、启动、WebView2 缺失与卸载仍需 Windows 真机。

### 可延后

- 多单位、批次、数据权限、License、外部对接（Q4、Q5、Q17–Q19）：按目标客户与首发范围决定。
- Windows Authenticode 签名（2.7）：若首发仅 macOS，可延后。
- 6.9 额度值调整（2.5）：执行逻辑已落地，额度数值随产品调整。
- 物理删除与同步目录拒绝写入（2.8、2.9）：软删与告警已可接受。
