# 更新模块拆分重构方案

> 目标：把「检测 / 编排 / 平台安装」彻底分层，消除 mac 壳与 win 壳各写一份
> 更新状态机导致的双胞胎 bug（2026-11 连续三次闪退/显示问题均属此类）。
> 状态：已评审通过。P0（core/update_engine 编排层 + 假依赖回归）已完成；
> P1 win 壳接入、P2 mac 壳接入、P3 前端统一 normalize 待逐阶段发布。基线版本 1.0.15。

## 1. 现状与问题

| 层 | 现状 | 问题 |
| --- | --- | --- |
| `core/update`（update.h/update.cpp/update_signature.cpp） | 纯判定：清单解析、验签、版本比较、灰度、冷却、退避、安装/恢复判定 | 无。已是共用检测模块，保持不动 |
| `shell/mac/updater.mm`（约 2000 行） | 检测判定 + 状态机 + NSURLSession 下载 + DMG 挂载替换 + 持久化 + 桥接序列化全部混写 | 与 win 各写一份编排逻辑 |
| `shell/win/updater_win.cpp`（约 950 行） | 同上（WinHTTP + BCrypt + ShellExecute 静默安装） | 同上 |
| `web/app.js` | 为 win/mac 各写一套状态 normalize 与渲染 | 字段口径漂移无门禁 |

近三次线上问题的根因都落在「平台无关却写了两遍」的部分：
- win 的 `download_progress` 不落盘 → 重启后显示「0 B」（1.0.15 修）
- 清单换版后陈旧 pending 不清除 → 误装旧包（1.0.15 修）
- 安装前不重校验包体 → 坏包照跑、程序先自杀（1.0.15 修）
- mac 侧历史上同类问题独立存在（冷却值、验证期回退），两仓互不同步

## 2. 目标架构

```
┌─────────────────────────────────────────────┐
│ core/update（已有，检测层，纯函数）           │
│   parse_manifest / evaluate / rollout /      │
│   cooldown / retry / decide_install / 验签    │
├─────────────────────────────────────────────┤
│ core/update_engine（新建，编排层，平台无关）  │
│   状态机 + 持久化 schema + 进度聚合           │
│   + 统一状态 JSON + 规则：清单变更→pending    │
│   作废、安装前重校验、退避计时                │
│   依赖注入：ITransport / IHasher / IInstaller│
├──────────────────────┬──────────────────────┤
│ shell/mac 端口(薄)    │ shell/win 端口(薄)    │
│  NSURLSession 下载    │  WinHTTP 下载          │
│  SecTransform SHA256  │  BCrypt SHA256         │
│  DMG 挂载→替换→自重启 │  ShellExecute 静默安装 │
│  Sparkle appcast 兼容 │  updater_win.json 兼容 │
└──────────────────────┴──────────────────────┘
```

### 2.1 检测模块（core/update，不动）

保持纯函数 + ctest 覆盖。新增内容只允许是判定规则，禁止引入 I/O。

### 2.2 编排模块（core/update_engine，新建）

文件：`core/include/xiaotu/update_engine.h`、`core/src/update_engine.cpp`。

接口（草案）：

```cpp
struct ITransport {                      // 拉清单 / 下载产物
  virtual bool fetch(const std::string& url, std::string& body,
                     std::string& err) = 0;
  virtual bool download(const std::string& url, const fs::path& dest,
                        ProgressCb on_chunk, CancelCb cancel,
                        std::string& err) = 0;   // 写 dest.part，成功后原子改名
};
struct IHasher {
  virtual bool sha256_file(const fs::path& p, std::string& hex) = 0;
};
struct IInstaller {                      // 平台语义全部关在这里
  virtual InstallResult install(const PendingPackage&) = 0; // mac: 挂载替换自重启
                                                     // win: ShellExecute /VERYSILENT
  virtual bool verify_before_install(const PendingPackage&,
                                     std::string& reason) = 0; // 引擎统一调用
};
class UpdateEngine {                     // 两壳共用唯一状态机
 public:
  struct Deps { ITransport*; IHasher*; IInstaller*; IClock*; IStore*; };
  void check(bool manual);               // 冷却/退避/清单变更→pending 作废
  void download_pending();               // 断点清理、进度聚合、SHA 校验
  bool try_install();                    // 强制安装前重校验
  std::string status_json();             // 唯一对外状态口径（见 2.4）
};
```

引擎内置规则（都是这次踩过坑的）：
1. 清单 `setup_sha256` 变化 → 作废旧 pending、状态回 IDLE（防误装旧包）
2. 任何进入 INSTALLING 前 → 重校验大小 + SHA256（防坏包自杀式安装）
3. 下载一律 `*.part` + 原子改名；失败必须删除半截文件
4. 进度字段与 `pending_size` 同步落盘（防重启后「0 B」）
5. 冷却/退避计时用注入的 `IClock`，可测

### 2.3 平台模块（两壳，变薄）

- mac：`updater.mm` 只留 NSURLSession/SecTransform/DMG 流程 + WKWebView 桥接；
  Sparkle appcast 兼容逻辑保留在端口层（引擎不感知 Sparkle）。
- win：`updater_win.cpp` 只留 WinHTTP/BCrypt/ShellExecuteW + `updater_win.json`
  旧格式读写适配器；`.iss` 的静默安装/重启语义不变（那是平台差异本体，不抽象）。

### 2.4 前端契约统一

引擎输出唯一 `status_json`（字段：state、version、build、bytes_total、
bytes_done、pending_path、pending_size、retry_after、last_error…）。
`app.js` 合并 `normalizeWinUpdateStatus` 与 mac 分支为一个 `normalizeUpdateStatus`，
mac/win 只按 `platform` 微调文案。新增 ctest：status_json 字段集合快照断言。

## 3. 迁移步骤（每步独立可发布、可回滚）

| 阶段 | 内容 | 验证 |
| --- | --- | --- |
| P0 | 引擎骨架 + 假依赖单测（状态机全路径、5 条内置规则） | 新 ctest，不动壳，零风险 |
| P1 | win 壳接入引擎（端口实现三接口；`updater_win.json` 读写兼容旧文件） | Windows CI + 实机升级 1.0.15→1.0.16 全链路 |
| P2 | mac 壳接入引擎（DMG 流程进 IInstaller；Sparkle 保持旁路） | mac 出包 + 实机升级验证 |
| P3 | 前端统一 normalize；删两壳残留的私有状态字段 | node --check + 双平台 UI 手测 |

约束：
- 迁移期间不改任何用户可见行为；行为修复与重构**永不混在同一发布**
- 每阶段引擎规则先写 ctest 再实现（TDD），把 1.0.15 修的三个 bug 全部做成回归用例
- P1/P2 各占一个 minor 版本窗口，出问题回滚 = 壳端口切回旧文件（引擎无状态残留）

## 4. 风险与取舍

1. **不统一安装语义**：mac「替换自重启」与 win「安装器杀壳再拉起」是平台事实，
   强行抽象会造出泄漏抽象；只统一「何时允许安装」的判定（引擎）与「怎么装」
   （端口）。
2. **旧持久化文件兼容**：两壳现有 JSON 必须能被新引擎读取（升级用户状态不丢），
   各写一个一次性迁移适配器，P3 删除。
3. **Sparkle 旁路**：appcast 供老内测客户端，不进引擎；引擎只管 v2 清单。
4. **发布窗口**：建议 P0 随下个任意版本合入（纯新增），P1 单独发版，P2 再单独发版。

## 5. P1 win 端口落地契约（实现依据）

引擎（`core/update_engine`）已在 P0 落地并 25/25 ctest 全绿。P1 把
`shell/win/updater_win.cpp` 改造成「端口 + 适配器」，对用户可见行为零改动。

### 5.1 三个接口的 win 实现

- `ITransport::fetch` → 复用现有 `winhttpGet(url, body, ...)`。
- `ITransport::download` → 复用 `winhttpGet` 的 `on_chunk` 版：写 `dest.part` →
  每块调 `on_progress(downloaded, total)` → 完成 `_wrename` 到 dest；`cancel()` 为真
  则中断返回 false（半截文件由引擎删除，规则 3）。
- `IHasher::sha256_file` → 复用现有 `UpdaterWin::sha256File`（BCrypt，小写 hex）。
- `IInstaller::install` → 现有 `ShellExecuteW(open, path, "/VERYSILENT /SUPPRESSMSGBOXES
  /NORESTART /SP- /CLOSEAPPLICATIONS /RESTARTAPPLICATIONS", SW_HIDE)`；`>32` 视为 STARTED。
- `IClock::now_epoch` → `epochNow()`。
- `IStore` → 读写 `%LOCALAPPDATA%\com.simem.xiaotu\updater_win.json`（路径不变）。

### 5.2 EngineConfig 取值

- `platform="windows"`、`channel` 沿用旧值、`install_id` 沿用旧值（空则 generateUuid）。
- `current_version=""`/`current_build=0` → 引擎回落编译值（与旧壳同口径）。
- `manual_cooldown_seconds=0`（旧壳 checkNow 无手动冷却，保持行为）；
  `auto_check_interval_seconds=86400`（旧壳 24h±2h 抖动由壳的 autoCheckLoop 保留，
  引擎只管 next_check_epoch 兜底）。
- `ignore_min_os=true`：旧 win 壳 v2 路径不查 min_os，保持行为不变。
- `public_key_base64=XIAOTU_UPDATE_PUBKEY`（CMake 注入；空则引擎跳过验签，同旧壳）。
- `download_dir` = 旧 `downloadDir()`。

### 5.3 旧 updater_win.json → 引擎 schema 一次性迁移（load 前读旧键）

旧文件键与引擎键基本同名（manifest_version/build/sha256/size/setup_url、pending_size、
skipped_version、skip_until_epoch、install_id、channel、last_result、last_error、
consecutive_failures、next_check_epoch 直接读）。差异项：

| 旧键 | 引擎键 | 迁移规则 |
| --- | --- | --- |
| `download_state` | `state` | RUNNING→DOWNLOADING；DONE→DONE；FAILED→FAILED；IDLE→IDLE |
| `pending_local_path` | `pending_path` | 同值 |
| `download_progress` | `bytes_done` | 解析 `"a/b"` 取 a；无则 0 |

迁移在 `load()` 之后做一次适配（引擎读自身 schema；旧键名由壳补齐进引擎状态），
P3 删适配器。引擎 `load()` 已内建崩溃恢复与残留 pending 清理，覆盖旧壳构造函数里
的两段逻辑。

### 5.4 桥方法映射（对外签名与返回码不变）

- `checkNow(cb)` → `engine.check(manual=true)`；UPDATE_AVAILABLE→cb("UPDATE_AVAILABLE",version)，
  无更新→cb("NO_UPDATE","")，失败→cb("FETCH_FAILED"/"MANIFEST_PARSE_ERROR"/"SIGNATURE_INVALID"/
  "MANIFEST_INVALID"/"NO_UPDATE"…)。
- `downloadUpdate(cb)` → 后台线程 `engine.download_pending()`；成功 cb("DOWNLOADED")，
  取消 cb("CANCELED")，失败 cb("FAILED", last_error)。`statusJson` 的 download_state/
  download_progress 由引擎 state/bytes_done/bytes_total 反推（保持旧串格式 `"a/b (x%)"`）。
- `installUpdate(cb)` → `engine.try_install()`；started→cb("STARTED")，NO_PENDING_UPDATE→
  cb("NO_PENDING_UPDATE")，VERIFY_FAILED→cb("NO_PENDING_UPDATE","PACKAGE_INVALID")，
  UNAVAILABLE→cb("UPDATE_UNAVAILABLE")，失败→cb("OPEN_FAILED", error)。
- `cancelPrefetch(cb)` → `engine.cancel_download()`；未在跑 cb("NOT_RUNNING")，否则 cb("CANCELED")。
- `setOptions(ac,pf,cb)` → `engine.set_options(true, ac, pf)`；cb("UPDATED")。
- `statusJson()` → 引擎 `status_json()` 经适配器补回旧壳独有键（download_state、
  download_progress、pending_local_path），前端 normalizeWinUpdateStatus 不改即可读。

### 5.5 验证

- Windows CI（windows-build.yml）：编过 + ctest 全绿（含 update_engine_smoke）。
- 实机：1.0.15→1.0.16 全链路（检查→下载→重启后进度不丢→安装→装后残留清理）。
