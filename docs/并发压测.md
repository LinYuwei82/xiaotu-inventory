# 并发压测

验证 10–30 个用户同时使用时的响应时间、错误率，以及并发下单据号与库存的一致性。脚本只用 Python 标准库，对着已经启动的网络版服务跑。

## 1. 复现方法

```bash
# 1. 准备一个干净的数据目录并设置管理员口令
./build/release/server/xiaotu-server --data /tmp/xt-load2 --set-password admin

# 2. 启动网络版
./build/release/server/xiaotu-server --server --port 18121 --data /tmp/xt-load2

# 3. 12 个并发用户，跑 20 秒，并打开数据库核对
XIAOTU_PASSWORD='AdminPassw0rd!' python3 tools/loadtest/mixed_load.py \
  --base http://127.0.0.1:18121 --users 12 --duration 20 --db /tmp/xt-load2/app.db

# 4. 30 个用户（含 admin 不超过 30 个账号上限，所以填 29）
XIAOTU_PASSWORD='AdminPassw0rd!' python3 tools/loadtest/mixed_load.py \
  --base http://127.0.0.1:18121 --users 29 --duration 20 --db /tmp/xt-load2/app.db
```

脚本是幂等的：压测商品（`LOAD-ITEM-1..4`）、供应商、客户与 `loadNN` 账号重复运行会复用；每个商品会先入库 20 万件，保证出库不会因为缺货而出现预期内的失败。

## 2. 负载构成

每个线程先登录，全部登录完成后同时开跑（避免登录风暴混进稳态延迟），随后按固定权重循环：

| 操作 | 说明 | 占比 |
| --- | --- | --- |
| 采购入库 | 创建并直接审核一张 `PUR_IN` | 2/7 |
| 销售出库 | 创建并直接审核一张 `SAL_OUT` | 2/7 |
| 草稿 + 审核 | 先存草稿再审核 `PUR_IN`，覆盖两步链路 | 1/7 |
| 报表 | `GET /api/reports/stock-balance` | 1/7 |
| 单据列表 | `GET /api/documents?doc_type=PUR_IN` | 1/7 |

结束后自动核对四项：

1. 接口返回的 `doc_no` 无重复；
2. `doc_header` 表内 `doc_no` 无重复；
3. 每个 `(仓库, 商品)` 的 `stock_balance.qty` 等于 `stock_ledger` 求和；
4. 库存数量等于「压测前基线 + 本次成功入库 − 本次成功出库」；
5. `doc_seq` 当日已分配序号等于当日单据数。

任一项不通过或出现请求错误，脚本退出码为 1。

## 3. 测试环境

- Apple M4 / 16 GB / macOS 15.8.2，服务端与压测脚本同机（回环网络）。
- Release 构建，SQLite 单写连接 + 4 个读连接，httplib 线程池 9 线程。

同机回环不代表真实局域网或低配服务器，但足以暴露并发逻辑与调度缺陷。

## 5. 压测发现并修复的缺陷

**现象**：修复前同样的 12 并发场景，登录的 p90 与最大值都是 5.24 秒，其余操作也偶发数秒延迟。

**定位**：给服务端登录入口加临时时间戳后发现，客户端 19:21:34.870 发出请求，服务端 5.1 秒后才进入处理函数；`Db::read` 与 Argon2 校验本身都低于 500 ms。问题在请求到达业务代码之前。

**根因**：httplib 的线程池是「一个连接占一个线程直到连接结束」。线程池大小是 `max(8, CPU 数 − 1)`，本机 9 个。默认 keep-alive 复用下，处理完请求的线程会在套接字上等下一个请求，最长等 `CPPHTTPLIB_KEEPALIVE_TIMEOUT_SECOND = 5` 秒。浏览器每个页面会开多条连接，连接数一超过线程池，新请求就要排队到有线程空出来，最坏就是 5 秒。

**修复**：`server/src/http_server.cpp` 设置 `set_keep_alive_max_count(1)`，每个连接只处理一个请求后关闭，线程立即归还；局域网内新建连接的开销远小于排队。修复后同一场景 p99 从 5.2 秒降到毫秒级，吞吐仍在 1500 req/s 以上。

压测脚本的 HTTP 客户端会识别 `Connection: close` 并主动重连，避免在已关闭的套接字上重试。

## 6. 结论与边界

- 10–30 并发用户在单机场景下满足：0 错误、单据操作 p99 < 100 ms、登录 p99 < 0.5 s。
- 单据号、库存余额、库存流水在并发审核下保持一致，没有超卖或重复单号。
- 瓶颈在写串行化（SQLite 单写连接），吞吐约 1500–1800 req/s，远高于小规模用户的实际需求。
- 未覆盖：多进程同时写同一个库（SQLite 单文件不支持，部署文档已注明）、断网/弱网、长时间（小时级）浸泡测试与内存增长。需要时在此基础上加时长即可。
- 本次数据来自 macOS 开发机。Linux 服务器通常核数更少，绝对吞吐会低一些，但并发正确性结论不受平台影响。
