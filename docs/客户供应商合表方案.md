# 客户与供应商合表方案

> 状态：**第二步（建表与 1:1 迁移）已落地为 v28**；第三步「合并动作」与界面收口尚未开始。
> 版本说明：方案撰写时预留的 v27 已被「打印纸型与缩放」占用，实际合表迁移顺延为 **v28**。
> 本轮范围：只建 `partner` / `partner_legacy_map` 并做 1:1 搬运；`customer` / `supplier` 原地保留且继续可读写；`partner_key` 仍为 `C:` / `S:` / `T:`，`doc_header` / `ar_ap_entry` / `settlement` 的引用一律不改；不做任何自动合并。
> 目标：把 `customer` / `supplier` 两张结构几乎相同的档案表合并为一张 `partner`，客户、供应商两个菜单与既有单据流程保持不变。

## 0. 结论先行

1. **新建 `partner` 一张表**，用两个布尔位 `is_customer` / `is_supplier` 表达「客户 / 供应商 / 兼两者」，不用枚举。
2. **客户 id 原样保留为 partner id**，供应商按顺序分配新 id；用 `partner_legacy_map` 记录旧 id → 新 id，保证可回溯。
3. `doc_header.customer_id`、`doc_header.partner_id`、`ar_ap_entry.partner_id` **保留列，值改指 partner.id**；`partner_key` 统一改成 `P:{partner_id}`，`T:{名称}` 的自由文本口径保留。
4. **完全同名不自动合并**。自动合并只认「税号相同」或「名称 + 电话都相同」；同名只有人工确认才能合。
5. 分四步：**只读重复预览 → v27 建表与 1:1 迁移 → 人工/批量合并 → 界面收口与旧表下线**。不要「建表 + 合并」一起上。
6. 迁移本身在单事务内，失败自动回滚；但迁移器**不会自动备份**，实施前必须用现有 `backup_database` 做全量备份。

## 1. 目标形态

### 1.1 `partner` 表字段

```sql
CREATE TABLE partner (
  id                 INTEGER PRIMARY KEY,
  code               TEXT    NOT NULL,
  name               TEXT    NOT NULL,
  contact            TEXT    NOT NULL DEFAULT '',
  phone              TEXT    NOT NULL DEFAULT '',
  address            TEXT    NOT NULL DEFAULT '',
  tax_no             TEXT    NOT NULL DEFAULT '',
  is_customer        INTEGER NOT NULL DEFAULT 0,  -- 1 表示可按客户使用
  is_supplier        INTEGER NOT NULL DEFAULT 0,  -- 1 表示可按供应商使用
  credit_limit_cents INTEGER NOT NULL DEFAULT 0,  -- 仅 is_customer=1 时生效
  credit_days        INTEGER NOT NULL DEFAULT 0,  -- 账期天数，0=不自动推算；本期新增占位
  merged_into        INTEGER NOT NULL DEFAULT 0,  -- 被合并进哪个 partner，0=未合并
  status             INTEGER NOT NULL DEFAULT 1,
  is_deleted         INTEGER NOT NULL DEFAULT 0,
  created_at         TEXT    NOT NULL,
  created_by         TEXT    NOT NULL DEFAULT 'system',
  updated_at         TEXT    NOT NULL,
  updated_by         TEXT    NOT NULL DEFAULT 'system',
  CHECK (is_customer IN (0, 1)),
  CHECK (is_supplier IN (0, 1)),
  CHECK (status IN (0, 1)),
  CHECK (is_deleted IN (0, 1)),
  CHECK (is_customer = 1 OR is_supplier = 1)
);
CREATE UNIQUE INDEX uk_partner_code ON partner(code);
CREATE INDEX idx_partner_name ON partner(name);
CREATE INDEX idx_partner_tax_no ON partner(tax_no) WHERE tax_no <> '';
```

字段来源对照：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `code` / `name` / `contact` / `phone` / `address` / `status` / 审计列 | customer + supplier | 两边字段完全一致，直接合并 |
| `tax_no` | customer + supplier（v19 两边都加） | 合并为一个字段；唯一性不强制，重复靠预览识别 |
| `credit_limit_cents` | 仅 customer（v19） | 只对 `is_customer=1` 有意义；取消客户角色前必须校验应收余额为 0 |
| `credit_days`（账期） | **当前不存在** | 现状是每张单据自己填 `ar_ap_entry.due_date`，档案上没有账期字段。本期只建列、置 0、不参与计算，避免合表时凭空造业务规则 |
| `is_customer` / `is_supplier` | 新增 | 表达客户 / 供应商 / 兼两者 |
| `merged_into` | 新增 | 合并后保留被并方记录，用于撤销合并与追溯 |

### 1.2 类型表达

- API 与页面统一输出三个派生值：`is_customer`、`is_supplier`、`type`（`customer` / `supplier` / `both`）。
- 不再使用枚举 `partner_type`。原因：兼买卖是常态，枚举每增加一种组合都要改 CHECK、改前后端判断；两个布尔位可直接用于 SQL `WHERE is_customer = 1`。
- 约束：至少一个角色为 1；两个角色都取消时拒绝保存（要么停用 `status=0`，要么删除）。

### 1.3 兼容视图（过渡期）

v27 把旧表改名后，建立只读视图，让尚未改完的报表 SQL 继续可读：

```sql
CREATE VIEW customer AS
  SELECT id, code, name, contact, phone, address, status, is_deleted,
         created_at, created_by, updated_at, updated_by, tax_no, credit_limit_cents
  FROM partner WHERE is_customer = 1;
CREATE VIEW supplier AS
  SELECT id, code, name, contact, phone, address, status, is_deleted,
         created_at, created_by, updated_at, updated_by, tax_no
  FROM partner WHERE is_supplier = 1;
```

视图不可写。任何漏改的写入路径会**直接报错**而不是悄悄写坏数据，这是有意的。

| `doc_header.partner_id`（v3） | 指向 `supplier.id` | **保留列**，值通过 `partner_legacy_map` 重指到 partner.id |

| `ar_ap_entry.partner_id` | 客户或供应商 id | 按 map 重指；客户侧不变，供应商侧改写 |
| `ar_ap_entry.partner_key` | `C:{customer_id}` / `S:{supplier_id}` / 无档案时 `T:{名称}` | **改值**：`C:`/`S:` 统一改 `P:{partner_id}`；`T:` 保留 |

| 账龄（`core/src/report_service.cpp:561-604`） | 按 `partner_key` + `partner_name` 分组 | 不改 SQL，`P:` 键自然生效 |
| 期初应收/应付导入（`core/src/opening_import.cpp:352-368`） | 拼 `C:` / `S:` + partner_id | 改拼 `P:{partner_id}` |
| 收付款录入/核销（`core/src/settlement_service.cpp:176-223`） | `partner_key` 字符串匹配 | 不改逻辑；页面传 `P:` 前缀；旧 `C:`/`S:` 由兼容分支兜底 |
| Excel 导入导出（`core/src/masterdata_io.cpp:34-37, 128-152, 680-698`） | 两套模板：客户 8 列（含信用额度）、供应商 7 列 | **保留两套模板与列**；后端都写 `partner`，按菜单设置角色；导出仍按角色过滤。编码冲突见 §4.4 |
| 生成代码（`tools/codegen/schema/masterdata.json`） | `customer` / `supplier` 各生成 DAO/Service/Route/Page | 改为 `partner` 生成一套；客户/供应商页面改成按角色过滤的只读别名（见 §5.3） |
| 权限（`core/src/migrations.cpp` v3/v7 授权） | `customer.read/write`、`supplier.read/write` | **保留原权限**，两个菜单沿用；合并后的 `partner` 服务接受任一角色权限。审计 `entity` 统一写 `partner`，`detail` 里记录角色变化 |

**一句话**：列都留着，值改指新表；唯一必须改值的是 `partner_key` 字符串。

## 3. 重复单位怎么识别

### 3.1 规范化

- 名称：去首尾空白、连续空白折叠为一个、全角转半角；比较时忽略英文大小写。
- 电话：去掉空格、`-`、`(`、`)`，去掉前缀 `+86`。
- 税号：全角转半角、转大写、去掉空格与 `-`。

### 3.2 匹配优先级与动作

| 优先级 | 规则 | 置信度 | 动作 |
| --- | --- | --- | --- |
| 1 | 双方税号非空且规范化后相等 | 高 | 默认建议合并，可批量确认 |
| 2 | 名称规范化相等 **且** 电话规范化相等（均非空） | 中高 | 默认建议合并，可批量确认 |
| 3 | 名称规范化相等，但税号/电话缺失或冲突 | 中 | **必须人工确认**，不自动合并 |
| 4 | 名称高度相似（一方包含另一方，或编辑距离 ≤ 1）且电话相同 | 中低 | 只提示，人工判断 |
| 5 | 其他 | — | 不提示 |

**完全同名要不要自动合？不自动。**
理由：同名不同法人、加盟店、门店与总公司同名很常见；两边都可能已有往来余额，误合后拆分要改单据、改台账、改对账单，代价远高于人工点一次确认。
唯一可批量确认的例外：双方都无税号、无电话、且两边 `ar_ap_entry` 均无记录（无余额、无单据），预览页提供「一键确认」按钮，仍需人工触发。

阻断项（即使税号相同也不直接合）：

- 两边税号都非空且不相等 → 标记冲突，人工处理。
- 一边已停用/已删除 → 单独标记，不参与自动建议。
- 合并后编码冲突且用户未选择处理方式 → 停在预览，不执行。

### 3.3 合并前预览表

新页面「往来单位归并预览」，只读，不写库。每行一个旧档案：

| 列 | 来源 |
| --- | --- |
| 侧别 | 客户 / 供应商 |
| 旧编号 | `customer.code` / `supplier.code` |
| 名称 | 档案名称 |
| 税号 | 档案税号 |
| 电话 | 档案电话 |
| 应收余额（元） | `SUM(amount_cents - settled_cents)`，`direction=1`、`status<>'VOIDED'` |
| 应付余额（元） | 同上，`direction=-1` |
| 应收单据数 | `COUNT(DISTINCT doc_id)`，`direction=1`、`doc_id>0` |
| 应付单据数 | 同上，`direction=-1` |
| 期初笔数 | `doc_id=0` 的期初记录数 |
| 匹配依据 | 税号 / 名称+电话 / 仅名称 / 相似名称 |
| 置信度 | 高 / 中高 / 中 / 低 |
| 建议动作 | 合并 / 人工确认 / 保留 |
| 目标 partner | 建议并入的 partner 编号（空表示新建） |

余额与单据数直接从 `ar_ap_entry` 聚合，不能从档案表推算：

```sql
SELECT partner_key, partner_name,
       SUM(CASE WHEN direction = 1  AND status <> 'VOIDED' THEN amount_cents - settled_cents ELSE 0 END) AS ar_open,
       SUM(CASE WHEN direction = -1 AND status <> 'VOIDED' THEN amount_cents - settled_cents ELSE 0 END) AS ap_open,
       COUNT(DISTINCT CASE WHEN direction = 1  AND doc_id > 0 THEN doc_id END) AS ar_docs,
       COUNT(DISTINCT CASE WHEN direction = -1 AND doc_id > 0 THEN doc_id END) AS ap_docs,
       SUM(CASE WHEN doc_id = 0 THEN 1 ELSE 0 END) AS opening_rows
FROM ar_ap_entry
GROUP BY partner_key, partner_name;
```

预览支持导出 CSV / XLSX，便于线下会签后再执行。

## 4. 迁移步骤

### 4.1 第 0 步：预检与全量备份（必做）

1. 停写：单机版退出程序，网络版停服务；确认没有其他进程打开 `app.db`。
2. `PRAGMA integrity_check` 必须为 `ok`；检查磁盘剩余空间大于数据库文件 2 倍。
3. 记录基线（写入迁移日志，便于事后核对）：
   - `customer` / `supplier` 行数；
   - `doc_header` 中 `customer_id>0` / `partner_id>0` 的行数；
   - `ar_ap_entry` 按 `direction` 的 `COUNT(*)`、`SUM(amount_cents)`、`SUM(settled_cents)`；
   - `settlement` 按 `direction` 的条数与金额。
4. 用现有备份工具做全量备份：`core/src/masterdata_io.cpp:587` 的 `backup_database(db, data_dir/"backups", "pre-partner")`。备份失败即中止。
5. 先在数据库副本上完整跑一遍迁移与核对，再动生产库。

### 4.2 第 1 步：v28 建表与 1:1 迁移（单事务）

> 本轮实际落地：只做下面第 1–4 项（建表、客户/供应商 1:1 搬运、编码冲突处理）与 `partner_legacy_map`；第 5 项「重指引用」与第 6 项「旧表改名 + 兼容视图」留到后续步骤，`partner_key` 仍是 `C:` / `S:` / `T:`。

迁移器对每条迁移使用 `BEGIN IMMEDIATE`，异常自动 `ROLLBACK`（`core/src/migrations.cpp:889-909`），所以本步整体可回滚。

1. 建 `partner`、`partner_legacy_map`、`partner_merge_log`。
2. 客户 1:1 迁入：
   - `partner.id = customer.id`（保留客户 id）；
   - `is_customer=1`、`is_supplier=0`；
   - `credit_limit_cents`、`tax_no` 原样带过来。
3. 供应商 1:1 迁入：
   - 默认不复用 id，`id = max(partner.id)` 递增，按 `supplier.id` 排序保证可重复；
   - `is_supplier=1`、`is_customer=0`；
   - 写入 `partner_legacy_map('supplier', old_id, new_id)`。
4. 编码冲突处理：`partner.code` 全局唯一。客户编码优先保留；供应商编码若冲突，追加 `-S` 后缀并在预览/日志中列出。默认规则可配置，但迁移中必须确定，不能留空。
5. 重指引用（同一事务）：
   - `doc_header.partner_id = map.partner_id`（仅供应商单据，即 `partner_id>0`）；
   - `ar_ap_entry.partner_id = map.partner_id`；
   - `ar_ap_entry.partner_key`：`C:{id}` → `P:{id}`；`S:{id}` → `P:{new_id}`；`T:` 不变；
   - `settlement.partner_key` 同上。
6. 旧表改名 `customer_legacy` / `supplier_legacy`，建 §1.3 的两个只读视图。
7. 迁移内只做 1:1，**不做任何合并**。

### 4.3 可回滚性

- 失败：事务回滚，`schema_migration` 不写入 v27，数据库停留在 v26。
- 手工回退（仅限尚未发生合并、且没有新数据写入 partner 的情况）：
  1. `DROP VIEW customer; DROP VIEW supplier;`
  2. `ALTER TABLE customer_legacy RENAME TO customer;` 供应商同理；
  3. 删 `partner_merge_log`、`partner_legacy_map`、`partner`；
  4. `DELETE FROM schema_migration WHERE version = 27;`，`PRAGMA user_version = 26;`
- 已经发生过合并或产生新数据：**只接受备份恢复**，不再提供反向 SQL。

### 4.4 第 2 步：合并（独立动作，不在迁移里）

- 每次合并一个事务，写 `partner_merge_log`：`into_partner_id`、`from_partner_id`、合并前双方编号/名称/税号/余额快照、操作人、时间。
- 被合并方保留记录：`is_deleted=1`、`merged_into=into_id`；列表默认过滤。
- 引用重指：`doc_header` 相应 id、`ar_ap_entry.partner_id/partner_key`、`settlement.partner_key` 全部从 `from` 改到 `into`。
- 撤销合并：仅当合并后 `ar_ap_entry` / `settlement` / `doc_header` 没有新增记录时允许；新增过则拒绝并提示走人工调账。
- 合并前必须显示 §3.3 预览行的双方余额与单据数，确认后执行。

### 4.5 历史同一单位两边都有记录时

- 若确认合并：客户侧单据 `customer_id` 不变，供应商侧 `partner_id` 指向同一个 partner.id；`partner_key` 统一 `P:id`，应收与应付仍按 `direction` 分开，互不抵消。
- 若不合并：保留为两个 partner（一个 `is_customer=1`，一个 `is_supplier=1`），键分别为 `P:{a}`、`P:{b}`，行为与现在一致。
- 对账单仍按方向出，兼买卖单位分别看应收、应付两张对账单；不做「往来净额」合并表。

## 5. 界面怎么保持不变

### 5.1 菜单

- 「客户」「供应商」两个菜单保留，权限仍是 `customer.read`、`supplier.read`（`web/gen/pages.json`）。
- `/api/customers`、`/api/suppliers` 保留为**按角色过滤的别名**，返回结构与现在一致，额外带 `is_customer` / `is_supplier` / `type`。
- 兼买卖单位同时出现在两个列表里。

### 5.2 表单

- 从「客户」进入：默认 `is_customer=1`、`is_supplier=0`，显示信用额度字段。
- 从「供应商」进入：默认 `is_supplier=1`、`is_customer=0`，隐藏信用额度字段。
- 表单增加「同时作为供应商 / 同时作为客户」勾选项：
  - 勾选后另一角色置 1，信用额度字段随 `is_customer` 显示；
  - 取消客户角色时，若该单位仍有未核销应收或历史应收单据，拒绝并提示先结清；
  - 取消供应商角色同理检查应付。
- 编码、名称、税号、电话、地址、启用在两个菜单里是同一份数据，改一处两处同步。

### 5.3 生成代码的处理

当前 `customer` / `supplier` 的 DAO、Service、Route、Page 全部由 `tools/codegen/schema/masterdata.json` 生成，手改会被 `generate.py --check` 判为漂移，`tools/ci/check.sh` 会失败。

方案：

- 在 `masterdata.json` 中用 `partner` 替换 `customer` / `supplier` 两张表定义，生成一套 `PartnerDao/PartnerService/PartnerRoutes/PartnerPage`。
- 给生成器加两个小能力（预计 30 行以内）：
  1. `"no_nav": true`：partner 不单独出菜单，避免多一个「往来单位」入口；
  2. `"nav_page": { "key": "customer", "role": "customer", "api": "/api/customers", "permission": "customer.read" }`：用同一个页面模板生成两个按角色过滤的页面脚本与菜单项。
- 若不改生成器，退路是接受多一个「往来单位」菜单，把客户/供应商降为筛选视图；这是产品变化，需要另行确认。
- 任何情况下**不手改** `core/src/gen/*`、`server/src/gen/*`、`web/gen/*`。

### 5.4 单据与报表入口

- 销售类单据仍拉 `/api/customers`，采购类仍拉 `/api/suppliers`，标签「客户 / 供应商」不变。
- 收付款、对账单的往来单位下拉仍按方向取对应别名接口，选项值前缀由 `C:` / `S:` 改为 `P:`。
- 报表筛选参数仍是 `customer_id` / `supplier_id`，值即 partner.id，前端无需改参数名。

## 6. 风险与工作量

### 6.1 最容易漏的地方

1. **`partner_key` 字符串匹配**（用户已点名）：
   - `core/src/document.cpp:800`（生成键）
   - `core/src/report_service.cpp:17-50`（档案名解析）、`:561-604`（账龄）、`:608-705`（对账单）
   - `core/src/finance_service.cpp:9-38`（台账筛选）
   - `core/src/settlement_service.cpp:176-223`（核销键）
   - `core/src/opening_import.cpp:352-368`（期初键）
   - 漏一处的结果：该单位从对账单/账龄里消失，或核销时提示「往来单位不一致」。
2. **打印与导出抬头**：单据打印用 `doc_header.customer` 快照，不受影响；但对账单标题走 `archive_name`，改档案名后会显示新名称。需在文档里写明「历史单据不变、对账单显示当前档案名」。
3. **信用额度**：id 共用后，必须同时校验 `is_customer=1`，否则供应商 id 可能被销售单误用。
4. **生成代码漂移**：`generate.py --check` 与 `check.sh` 会拦住手改；改造 schema 后必须整体重新生成。
5. **导入导出**：客户模板 8 列、供应商模板 7 列（`core/src/masterdata_io.cpp:34-37`），编码全局唯一后冲突处理必须明确；导入按编码匹配，不能按名称。
6. **权限与审计**：审计 `entity` 从 `customer` / `supplier` 变为 `partner`，按 entity 过滤的旧审计记录会分叉；建议保留旧记录原样，只在新写入时用 `partner`。
7. **升级与回退**：迁移器不自动备份；已发布迁移不可改（checksum 校验），v27 一旦发版就只能靠新迁移修正。
8. **停用/删除语义**：`is_deleted` 与 `status` 两套标记继续保留，合并用 `merged_into` 第三套标记，列表过滤条件必须三处一致。

## 7. 建议的落地顺序

1. **先做只读的「往来单位归并预览」**（不改表）：直接读现有 `customer` + `supplier`，用真实数据校准 §3.2 的阈值，产出 CSV 供业务会签。
2. **再做 v27 建表与 1:1 迁移**：不合并，只重指引用；带备份、核对 SQL、可回滚说明。上线后观察一个版本。
3. **最后做合并动作**：在预览结果基础上逐条或批量确认，写 `partner_merge_log`，支持条件撤销。
4. **收口**：切换生成代码与页面别名，观察一个版本后再下线 `customer_legacy` / `supplier_legacy` 与兼容视图。

不建议「建表 + 合并」一起上：规则未经真实数据验证时，合并会直接污染应收应付；先只读预览的代价最小。

## 8. 验收与核对清单

迁移后必须逐条通过：

- [ ] `SELECT COUNT(*) FROM partner` = 客户数 + 供应商数 − 已合并数。
- [ ] `SELECT direction, COUNT(*), SUM(amount_cents), SUM(settled_cents) FROM ar_ap_entry GROUP BY direction` 与迁移前完全一致。
- [ ] `SELECT COUNT(*) FROM ar_ap_entry WHERE partner_key NOT LIKE 'P:%' AND partner_key NOT LIKE 'T:%'` = 0。
- [ ] `SELECT COUNT(*) FROM settlement WHERE partner_key NOT LIKE 'P:%'` = 0。
- [ ] 每个 `P:{id}` 都能在 `partner` 找到记录。
- [ ] 每个 `doc_header.customer_id>0` 对应 `partner.is_customer=1`。
- [ ] 每个 `doc_header.partner_id>0` 对应 `partner.is_supplier=1`。
- [ ] 任取一个兼买卖单位：应收对账单、应付对账单的期初/发生/期末与迁移前一致。
- [ ] 超信用额度销售出库仍按 `config.toml [sales] credit_limit_mode` 拦截/警告。
- [ ] 客户/供应商 Excel 导出列不变，重新导入后编码、税号、信用额度一致。
- [ ] 历史单据打印抬头仍是当时的 `doc_header.customer` 快照。
- [ ] `bash tools/ci/check.sh` 全绿，`generate.py --check` 无漂移。

## 10. v28 落地记录
